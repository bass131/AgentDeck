# 20 — 위협 모델과 경계

컨트롤마다 「무엇을 막으려는가」를 먼저 정해야 강도를 고를 수 있다. 이 문서는 막을 대상을 둘로 나누고, 각각을 버티는 층을 정한다.

## 막을 대상 둘

| 대상 | 모습 | 지금까지 | 버티는 층 |
|---|---|---|---|
| 실수 | 에이전트가 의도 없이 위험한 꼴을 쓴다. 예: `git push origin HEAD:master`, 줄 이음으로 나뉜 명령 | 실제로 겪은 것은 모두 이쪽이다(G1·G3·G5·G6) | 에이전트 프로세스 안의 장치도 대부분 막는다. 가드, 설정 규칙, 분류기, 앱 카드 |
| 의도적 우회 | 웹 문서나 저장소 파일에 심긴 지시를 에이전트가 따른다(프롬프트 인젝션). 또는 막힌 일을 다른 꼴로 다시 시도한다 | 관찰된 적 없다. 경계선 위의 사례가 하나 있다. G5 독립 검수자가 승인 질문이 뜬 명령을 자리표시자 글자로 바꿔 다시 실행했다 | 에이전트가 끌 수 없는 층만 버틴다 |

## 보호 수준 L0~L3

컨트롤을 에이전트가 고의로 끄려 할 때 얼마나 버티는지의 척도다. 한 컨트롤이 여러 길로 꺼질 수 있으면 가장 쉬운 길의 수준을 적는다.

| 수준 | 뜻 | 예 |
|---|---|---|
| L0 | 에이전트가 끌 수 없다. 에이전트 프로세스와 그 자격 증명 밖에 있다 | 에이전트 토큰에 없는 권한, 사람이 그 자리에서 하는 확인 |
| L1 | 앱 밖의 디스크 파일을 고치면 끌 수 있다 | 앱 설정·엔진 폴더, keyring의 토큰, 사용자 설정 `~/.claude/settings.json` |
| L2 | 에이전트가 일하는 저장소를 고치면 끌 수 있다 | `.claude/hooks/`, `.claude/settings.json`, 결정 보드 |
| L3 | 명령 글자만 바꾸면 지나간다 | 가드의 글자 판독, 설정 패턴 규칙 |

실수 대응에는 L3 장치로도 대개 충분하다. 의도적 우회에는 L0만 확실하다.
되돌리기 어려운 행위(병합, 배포, 보호 해제, 강제 push)는 L0으로 지킨다. 되돌릴 수 있는 행위는 L1~L3으로 지키고, 질문이 늘어나는 비용을 줄이는 쪽을 고른다.
이 원칙은 Second Brain 성향 29와 같은 결이다. 성향 29는 「게이트의 강도는 손상을 되돌리기 얼마나 어려운지에 맞춘다」는 사용자 성향이다.

## 같은 OS 사용자 문제

에이전트는 사용자의 Windows 계정으로 돈다. 그래서 사용자 계정이 읽고 쓰는 파일은 에이전트도 원리상 읽고 쓴다.

- keyring(Windows 자격 증명 관리자)에 저장된 `gh` 토큰은 `gh auth token` 한 줄로 나온다.
- Electron `safeStorage`(앱이 비밀값을 암호화해 저장하는 기능)는 Windows에서 DPAPI(사용자 계정 단위 암호화)를 쓴다. 같은 계정의 다른 프로세스도 복호화할 수 있다.
- 앱의 userData 폴더(앱 전용 데이터 폴더)와 엔진 폴더는 에이전트가 Bash로 쓸 수 있다(`10_현재-컨트롤-실사.md` 발견 6).

따라서 「앱만 쓰는 비밀과 설정」은 같은 계정 안에서는 L1에 머문다. L0으로 올리는 길은 셋이다.

1. **권한을 에이전트 쪽에서 없앤다.** 에이전트 세션에는 되돌리기 어려운 행위의 권한이 없는 자격 증명만 준다. 사람의 자격 증명은 디스크에 두지 않는다.
2. **사람이 그 자리에 있음을 매번 확인한다.** 병합 같은 행위 직전에 Windows Hello나 GitHub 기기 인증(브라우저에서 사람이 코드를 확인하는 로그인) 같은 확인을 요구한다. 에이전트는 이 확인을 대신할 수 없다.
3. **서버가 신원으로 가른다.** 에이전트가 사람과 다른 GitHub 신원으로 일하게 하고, 서버 규칙이 그 신원의 `master` 갱신을 거부하게 한다.

어느 길이 이 저장소(개인 소유 공개 저장소, 사람 한 명)에서 되는지는 `40_병합-분리.md`가 GitHub 공식 문서로 판정한다.

## 경계에 대한 결론

- 훅과 설정 규칙은 **실수 방지 장치**다. 보안 경계로 셈하지 않는다. M06 Backlog 20·21은 「가드가 놓치는 셸 꼴이 남았다」와 「가드를 키울지 다시 설계할지」였다. 이 설계의 답은 가드를 더 키워 의도적 우회를 막으려 하지 않는 것이다.
- 보안 경계는 L0 장치 셋이다. 에이전트 자격 증명의 권한 범위, 사람의 상호작용 확인, 그리고 그 둘이 갖춰진 뒤의 서버 보호다. 지금의 서버 보호는 에이전트 토큰으로 풀 수 있어 L0이 아니다(`10` 발견 1). `40`의 단계 B 뒤에야 L0이 된다.
- 앱 프로세스로 옮긴 컨트롤은 L1이다. 저장소 훅(L2~L3)보다 강하다. 엔진·설정의 쓰기 경로를 에이전트 도구에서 막으면 실수로 끄는 일은 거의 없어진다.
- 공식 문서도 같은 말을 한다. `auto` 모드는 「질문을 줄이지만 안전을 보장하지는 않는다」(https://code.claude.com/docs/en/permission-modes).
