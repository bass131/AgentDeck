## TL;DR

발단은 영호의 문제 제기(*"폴더 이름이 대충 방에 쓰레기 던져놓은 것마냥 체계화가 안 돼 있다"*)였는데, 착수 전 실측에서 진단이 뒤집혔다 — 규칙은 이미 있었고 파일 층은 폴더마다 일관돼 있었으며, 진짜 결함은 **규칙이 미이행인 채 `done`으로 기록된 것**(RF1 08 문서의 네 겹 모순)이었다. 그래서 이 마일스톤은 ① 규범을 ADR-039 하나로 정본화하고 ② 문서 폴더 11건 + 코드 stem 13건(+파생 테스트 10건)을 실제로 개명하고 ③ 재발을 명명 가드(advisory)로 막는 7 Phase가 됐다. 가장 값진 구조적 판단은 **순서가 안전이라는 것** — 훅의 경로 분류가 fail-open(정규식이 안 맞으면 '봉인 밖'으로 처리)이라 개명이 봉인을 조용히 푸는데, 신·구 병행 수용을 먼저 깔고(P03) → 개명하고(P05·P07) → 관대해진 수용을 일몰(P06)하는 순서로 그 함정을 피했다. 회귀 0으로 종결했고(G1~G6 전부 기준선 일치), 도중에 개명과 무관하게 이미 고장 나 있던 것들 — Codex doctor 판정기 결함, 테스트가 사용자 홈을 덮던 격리 결함, 두 엔진 봉인 비대칭 — 을 함께 닫았다. PR 2개(#29 docs · #30 code 스택)가 머지 대기 중이다.

## 5단계 보고

- 🎯 **무엇을 만들었나** — 저장소의 "이름 층"을 규범 하나로 정리했다. ① **ADR-039 신설**: 「전역 규칙은 폴더 이름 층이 소유하고, 파일명은 각 폴더의 계약이 소유한다」 + 개명 매니페스트 24건 + 역산 표 4축 ② **문서 폴더 11건** `NN_PascalCase` 개명(`harness→00_Harness` 등) ③ **코드 stem 13건** kebab→camelCase(`ipc-contract→ipcContract` 등, 파생 테스트 10건 동반 — 매니페스트 밖 파생물) ④ **명명 가드 신설**(advisory, 신규 생성물 한정 — `git ls-files` 판정) ⑤ 부수로 봉인·판정기·테스트 격리의 선재 결함을 봉합(백로그 17·19·20·22 해소, 18은 오탐 확정). 산출물 = 커밋 17개(계획 1 + docs 트랙 7 + code 트랙 6 + Codex 3), PR #29·#30.

- 🤔 **왜 필요한가** — 이름은 그냥 문자열이 아니라 **훅 정규식·권한 deny 목록·문서 포인터가 물고 있는 좌표**다. 혼재를 방치하면 새 파일마다 이름 판단이 갈리고, 개명을 하자니 안전장치가 이름에 걸려 있어 **개명 자체가 봉인을 조용히 푸는 작업**이 된다(HR2에서 실사고 — 안전장치 4곳 동시 무력화). 즉 이름 정리는 미용이 아니라 "무엇이 이름에 걸려 있는가"를 전수로 드러내고 그 걸림을 갱신하는 안전장치 점검이었다. 실제로 이 과정이 개명과 무관한 선재 결함들을 연쇄로 드러냈다.

- 🛠️ **어떻게 만들었나** — 골격은 셋이다. **첫째, 순서를 설계로 삼았다**: 병행 수용(P03) → 개명(P05·P07) → 일몰(P06). fail-open 환경에서 한쪽만 맞추면 개명 전후 어느 시점에 반드시 구멍이 생긴다. **둘째, 역산 표 4축**(①훅 fail-open ②기계 소비자 fail-visible ③봉인층 문서 ④Codex 어댑터)으로 "무엇을 바꾸나"가 아니라 **"그것이 무엇에 걸려 있나"를 먼저 전수 실측**하고, 실행 완료를 목록 대조로 판정했다. **셋째, 검증을 "테스트 green"이 아니라 "실제 발화"로 정의했다** — golden fixture(P03에서 표의 오판정을 red로 잡음), guard 로그 판정, canary 프로브, 뮤테이션 음성 대조. 안 고른 대안: 전역 파일명 획일화(이미 일관된 계약 4개를 동시에 깨서 기각), 치환 규칙 확장(개념형 ~35곳 오폭 — 열거 목록 표적 정리를 택함).
