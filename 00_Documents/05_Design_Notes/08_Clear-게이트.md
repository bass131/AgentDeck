# 쟁점 13 — Clear 게이트: Phase 경계 Context 리셋

**질문 한 문장**: `/clear`를 사람의 규율(C)에서 구조(H 또는 G)로 옮겨, "문서가 진실의 원천"(00장 원칙 4)을 선언이 아니라 매 Phase 실측되는 불변식으로 만드는 설계는 무엇인가?

## 발견 (2026-08-01, 영호)

- 사례: 어떤 시니어 개발자가 `/clear`(사용자 명시 호출 커맨드)를 Hook으로 자동화해서
  **Plan 설계 → 검증 → Clear(Hook으로 게이트화) → 작업 세션** 순서로 운영한다.
- 영호의 감탄 지점: Context Memory 관리를 극한으로 한다는 것.
- 카드 등재 결정: 2026-08-01, "그래 카드 파놓자".

## 핵심 독해 — 세 겹

1. **C → H 승격.**
   `/clear`는 원래 사람이 기억해서 치는 커맨드다 — 03장 스펙트럼으로 C(사람 체크포인트).
   사람이 잊으면 안 눌리고 세션은 조용히 썩는다.
   Hook화는 이것을 이벤트 매칭(H)으로 옮긴 것 — 카드 3·4와 같은 수(手)를 Context 위생에 적용한 사례다.
2. **원칙 4의 집행 장치.**
   "세션이 끊겨도 문서만으로 재개할 수 있다"는 세션을 실제로 안 끊으면 한 번도 검증되지 않은 백업이다 (복원 훈련 없는 백업).
   검증 통과 직후 Clear를 박으면 **모든 Phase 전환이 곧 재개 훈련**이 된다.
   Clear는 기억의 삭제가 아니라 **기억이 문서에 있다는 증명**이다 — 01장 "세션은 죽어도 디렉토리는 남는다"의 문자 그대로의 집행.
3. **확증편향의 시간축 분리.**
   계획을 짜던 Context가 구현에 들어가면 계획 과정의 합리화가 같이 들어간다.
   Clear 뒤의 세션은 계획서를 처음 읽는 독자로 읽는다 — 생성자·검증자 분리(검증 2)의 시간축 버전.

## 설계의 핵심 제약 — Clear가 안전한 지점은 한 곳뿐

아무 데서나 Clear하면 문서에 안 적힌 상태가 증발한다.
안전한 유일한 지점은 **검증 통과 직후** — 그 순간에만 "세션이 아는 것 ⊆ 문서가 적은 것"이 보증된다.
원칙 5(검증 통과 없이는 전진 없음)와 맞물리는 구조: **검증 게이트 = 영속화 증명 = Clear 자격**.
발견 사례의 순서(설계 → 검증 → Clear → 작업)가 우연이 아니라 필연인 이유다.

## 위험 — Clear는 계획 검증의 판돈을 키운다

- 문서에 구멍이 있으면, Clear 전 세션은 기억으로 때우지만 Clear 후 세션은 **모르는 걸 모르는 채로** 틀린 작업을 조용히 진행한다 (fail-open 방향).
- 따라서 두 가지가 한 세트로 설계돼야 한다:
  - **생존 목록** — 무엇이 Clear를 살아남아야 하는가: Phase-Steps 문서, work-pin(작업 좌표), 결정 대장(쟁점 04), 검증 기록(쟁점 03).
  - **재개 프로토콜** — Clear 직후 세션이 생존 목록을 로드했는지 확인하는 절차 (SessionStart 훅 후보).

## 부속 결정거리 (논의 때 확정)

- **구현 갈래**: 세션 내 Hook 자동 Clear(H) vs Phase마다 새 세션 스폰(스폰 조건 = G).
  어느 쪽이든 결정론 층이라 본질은 같다 — 선택은 도구 제약 실측과 함께 부트스트랩(쟁점 08) 몫.
- **Clear 지점의 전수**: ④ 계획 검증 통과 직후 한 곳인가, ⑤ 구현 루프의 매 Phase 검증 통과마다인가, ⑥ 회귀 검증 뒤에도인가.
- **비용**: 매 Phase 문서 재로드 토큰 비용 vs 썩은 Context를 끌고 가는 비용 — 트레이드오프 명시.
- **에스컬레이션과의 상호작용**: USER-INPUT 줄(쟁점 03)·문답 결과(쟁점 04)가 문서에 남는 한 Clear와 충돌하지 않음을 확인.

## 논의 추가 재료 (2026-08-01 확정 대화)

- **Clear의 대상은 메인 세션이다** — Worker는 스폰마다 새것이라, 이 카드가 바꾸는 것은 오케스트레이터의 수명 구조다.
- **훅의 프로그램적 clear는 공식적으로 불가** (실측: claude-code-guide 문서 확인).
  hooks-guide 명시: "The hook path always keeps the current conversation: it can't clear context and start a fresh implementation session."
  정확히 이 기능(자동 clear + 후속 프롬프트 주입)이 Issue #35150으로 요청됐다가 **not planned**로 종결. PostClear 훅(#44755)도 동일.
  훅은 stdout·exit code로만 말하고 슬래시 커맨드·도구 호출을 트리거할 수 없다.
- **"훅 자동 clear" 목격 사례의 실체** — 훅(신호) + 터미널 드라이버(실행)의 합성.
  훅이 백그라운드 드라이버를 띄우고, 드라이버가 CLI의 입력 대기 시점에 키 주입(tmux `send-keys` 등)으로 `/clear`+Handoff 프롬프트를 타이핑.
  문서 밖·플랫폼 의존(Windows 취약)·타이밍 의존이라 보장 수준이 H가 아님 — 실측 없이 H로 분류하면 지도가 거짓말한다.
- **G의 재정의** — 본질은 headless 여부가 아니라 **프로세스 교체로 Context를 물리적으로 버리는 것**.
  구현 두 갈래 모두 G: headless `claude -p` 연쇄(완전 무인, 공식 지원 — 일회성 = 한 프롬프트지 한 턴이 아님, 내부에서 도구·SubAgent 루프 완주) / Orca 태스크로 Phase마다 새 인터랙티브 세션(사람 개입 창구 유지).
- **`--resume` 금지** — headless의 세션 이어붙이기 옵션은 Context를 계승해 Clear 취지와 정반대. 재개는 문서로만.
- 드라이버형 자동 리셋(in-session)은 결국 "Context 버리고 문서 Handoff로 재시작" — G가 프로세스 교체로 더 깔끔하게 하는 일의 세션 내 흉내. 그래서 폐기가 아니라 **실측 후보**로 등재 (통과 시 대화형을 자동화로 승격).
- **세 번째 우회 — 훅-트리거 세션 재기동** (영호 질문 "훅으로 컨텍스트 초기화는 안 되나?"에서 도출):
  훅이 컨텍스트를 못 비우는 거지 **세션 프로세스를 끝내는 건 가능**하다(훅 = 셸 스크립트, 프로세스 제어 가능).
  훅이 감독자에 신호(또는 프로세스 종료) → 감독자가 Handoff 프롬프트로 새 세션 재기동 = G의 훅-트리거 구현.
  키 주입(타이밍·플랫폼 의존)보다 견고 — 드라이버 실측 후보 두 갈래 중 우선 검토 대상.
  참고: `/compact`(요약 압축)는 초기화가 아니라 **계승**이라 이 카드의 목적(확증편향 시간축 분리)에 부적합. Agent SDK로 자작 하네스를 짜면 컨텍스트가 자기 데이터라 자유 초기화 가능 — Orca 같은 ADE 층의 일반화.

## 결정

**확정 (2026-08-01, 영호)** — Clear 지점 = ④ 계획 검증 통과 직후 + ⑤ 매 Phase 검증 통과 직후 (⑥ 회귀 후는 리셋의 수혜자가 없어 제외).
규칙은 02장 **순서의 규칙 5**로 신설: "Context는 Phase 경계에서 리셋한다 — 검증 통과 직후에만."
강제 구조는 운용 모드별 이원화 — 대화형 = **리셋 게이트**(리셋 전까지 구현 도구 차단, 실행은 사람·잊으면 전진이 막힘) / 무인 = **Phase별 새 세션**(Handoff는 스폰 프롬프트).
재개는 생존 문서(Phase-Steps·work-pin·결정 대장·검증 기록)로만 — `--resume` 금지(fail-closed).
훅 신호 + 터미널 드라이버(tmux `send-keys`/Orca)의 자동 `/clear`+Handoff 주입은 **실측 후보** — 부트스트랩 실측 통과 시 대화형을 "사람이 침"에서 "드라이버가 침"으로 승격.

## 개정 1 — 실행은 무인이 기본 (2026-08-01, 영호)

근거는 M01 도그푸딩의 첫 사용자 실측이다: 사람 개입 지점 여섯 종류 중 다섯(clear 실행, 리셋·마감 게이트 장전, 검증 판정, 진행 GO)이 설계가 아니라 미구축 자동화의 대행이었고, "Human 개입 위치가 너무 많다"는 체감은 그 대행의 무게였다. 원 설계(00장 Layer 0)의 사람 위치도 본래 입구·예외·출구뿐이다.

- **실행 갈래의 기본값은 무인 — Phase별 새 세션.** 계획 검증 통과(④) 후 최종 보고까지 사람 체크포인트 없이 돈다. ④ 리셋은 의무 유지 — 계획 문답 세션과 첫 구현 세션의 절단이 곧 무인 진입이다.
- **대화형 리셋 게이트(H)는 보조 장치로 강등** — 도그푸딩·수기 모드 전용. 폐기가 아니라 무게 이동이다.
- **사람 개입의 정위치는 넷뿐**: 계획 문답(모호성·주도권 게이트) · 에스컬레이션(검증 4) · 비가역 승인(push 등) · 최종 보고.
- ⑤의 주기 논쟁(Phase 단위냐 마일스톤 단위냐, Context 게이지 트리거)은 무인 기본에서 소멸한다 — 세션이 Phase보다 오래 살지 않으면 사람이 Clear를 칠 일도, 핸드오프 마찰을 느낄 일도 없다. 마찰은 문서가 지고, 문서의 규격은 스폰 게이트가 기계로 강제한다.
- **파일럿(쟁점 09)의 실측 1순위 = 무인 드라이버** (Phase별 세션 스폰·Handoff·재기동). 드라이버 없이는 모든 실측이 수기로 돌아 같은 체감이 반복된다.

승격 반영 (2026-08-01, fetch 대조): 02장 순서 5 강제 구조 문단 개정 + 03장 순서 5 행·승격 경로 개정.
