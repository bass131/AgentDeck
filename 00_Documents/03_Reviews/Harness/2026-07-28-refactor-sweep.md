# 리팩토링 스윕 보고서 — 2026-07-28

## 이 문서는 무엇인가

오늘 AgentDeck의 production 코드 전체를 대상으로 리팩토링 스윕을 **진단 모드(dry-run)** 로 한 바퀴 돌렸다.
코드는 한 줄도 바꾸지 않았고, 커밋도 하나도 만들지 않았다.
다섯 명의 검토 에이전트가 영역별로 코드를 정독해서 "어디가 낡았고, 무엇을 고칠 가치가 있고, 무엇은 건드리면 안 되는가"를 조사한 결과가 이 문서다.
동시에 이번 실행은 새로 다듬은 스윕 절차(v3.1 초안)의 첫 실전 테스트이기도 해서, 절차 자체에 대한 피드백도 마지막에 붙였다.

읽는 순서 권장: **한눈에 보기 → 3장(보안 관련 3건) → 4장(고칠 가치 큰 10건) → 8장(지금 정할 것)**. 나머지는 필요할 때 참고.

## 한눈에 보기

**코드는 전반적으로 건강하다.**
보안과 구조의 치명적 위반(신뢰 경계 침범, 엔진 추상화 누수, 시크릿 노출, IPC 계약 이중 정의)은 다섯 영역 모두에서 **하나도 발견되지 않았다**.
테스트도 5,359개 전부 통과 상태다.

발견된 것은 "지금 사고 나는 문제"가 아니라 **"방치하면 수정 비용이 계속 올라가는 부채"** 다.
총 90건쯤 되는데, 성격은 크게 세 갈래다:

1. **보안 관련해서 미리 막아두면 좋은 것 3건** — 지금은 안전하지만 방어선이 한 겹뿐인 곳들 (3장)
2. **고치면 이득이 큰 구조 문제** — 같은 코드가 두 벌씩 있는 곳, 한 파일이 너무 많은 일을 하는 곳 (4장)
3. **건드리면 안 되는 것** — 중복처럼 보이지만 합치면 버그가 되는 코드, 자동 수정이 영구 금지된 영역 (5장)

이 보고서에서 각 발견에 붙은 라벨의 뜻:
**✅** = 저위험, 자동 적용해도 되는 것 / **🔶** = 구조를 바꾸는 것이라 적용 후 재검증이 필요한 것 / **⛔** = 자동 수정 영구 금지(사람 전용 트랙) / **📋** = 눈으로 봐야 판단 가능해서 제안까지만 하는 것.

## 1. 어떻게 진단했나

**측정 기준선(baseline)**: 시작 전에 회귀 게이트를 한 번 돌려서 현재 상태를 박제했다.
타입 검사(typecheck) node·web 양쪽 통과, 테스트 5,359개 통과·실패 0·스킵 10(스킵은 실제 API를 호출하는 live probe 계열 6파일 — 원래 스킵되는 게 정상), lint 오류 0.
코드를 안 바꿨으니 종료 시점 수치도 동일하다.

**우선순위 산정**: "큰 파일부터"가 아니라 **핫스팟** 순서로 봤다.
핫스팟이란 *복잡도(줄 수) × 변경 빈도(churn — git 이력에서 그 파일이 커밋에 등장한 횟수)* 가 높은 파일이다.
크지만 아무도 안 건드리는 파일은 부채여도 이자가 안 붙는 반면, 크고 자주 바뀌는 파일은 수정할 때마다 비용을 내고 있기 때문이다.

## 2. 영역별 상태 요약

- **shared (공용 계약, 17파일)** — 계약 규율이 잘 지켜지고 있다. 문제는 성장통이다: 이벤트 계약 파일 하나가 1,041줄까지 컸고, 실제 코드와 반대 내용을 말하는 낡은 주석이 2건 있다.
- **main (Electron 메인 프로세스, 62파일)** — 의존성 주입과 안전 게이트는 일관되게 우수하다. 대신 "거의 같은 코드 두 벌"이 9건으로 가장 많은 영역이고, 보안 관련 발견 3건(3장)이 전부 여기다.
- **backend (엔진 어댑터, 20파일 6,753줄)** — 엔진 고유 코드가 어댑터 밖으로 샌 곳은 없다(전수 확인). 부채가 `claudeAgentRun.ts` 한 파일에 집중돼 있다.
- **renderer (React UI, 232파일)** — 신뢰 경계 완벽 준수(권한 작업 직접 수행 0건, 전부 preload 화이트리스트 경유). 부채의 중심은 **단일 채팅 화면과 멀티 패널 화면이 같은 로직을 각자 한 벌씩 들고 있는 것**이다. 발견 수가 32건으로 가장 많다.
- **qa (테스트, 468파일)** — 죽은 테스트는 없다. 대신 "새 테스트를 만들 때 이전 테스트의 셋업 코드를 복사해서 변형하는" 관행이 쌓여서, 같은 목업(mock) 코드가 수십 개 파일에 복제돼 있다.

## 3. 보안 관련 발견 3건 — 지금은 안전하지만, 영호 판단이 필요하다

**① 파일 경로 검증이 한 겹뿐이다** — `main/02_fs/diff.ts:169`
이 함수는 "워크스페이스 루트 + 상대 경로"를 이어붙여 파일 경로를 만드는데, 그 상대 경로가 루트를 탈출하는지(`../` 같은 것) 자체적으로 검사하지 않는다.
지금은 이 함수를 부르는 유일한 곳(IPC 핸들러)이 호출 전에 검사를 해줘서 안전하다.
하지만 나중에 누군가 검사 없이 이 함수를 직접 부르면 그대로 경로 탈출 구멍이 된다.
**제안**: 함수 안에서도 한 번 더 검사하게 만들기. 겉보기 동작은 안 변하는 한 줄 수준의 보강인데, 보안 인접 코드라 영호 승인 후 진행이 원칙이다.

**② 창 크기 설정이 renderer의 입력을 검증 없이 믿는다** — `main/06_window/controls.ts:177`
renderer(신뢰하지 않는 쪽)가 보낸 창 크기·위치 값을 검사 없이 그대로 Electron에 넘긴다.
비정상 값(NaN, 음수, 화면 밖 좌표)이 오면 메인 프로세스에서 오류가 나거나 창이 화면 밖으로 사라질 수 있다.
같은 파일의 다른 함수들은 최소 크기 검사를 하고 있어서, 이 함수만 빠진 것이다.
**제안**: 값을 검사하고 범위를 벗어나면 무시하는 보정 함수 추가. 이건 동작이 실제로 바뀌는 수정이라 영호 확인이 필요하다.

**③ SDK 패키지 이름과 버전이 두 군데 중복돼 있다** — `engineState.ts` ↔ `engineVersions.ts` ↔ 어댑터
SDK 버전을 올릴 때마다 최소 두 곳을 같이 고쳐야 하고, 한 곳을 빠뜨리면 조용히 어긋난다.
다만 이 중복은 "엔진 관련 코드는 어댑터 밖으로 꺼내지 않는다"는 아키텍처 결정(ADR-003)을 지키느라 **의도적으로** 만든 것이라고 코드에 문서화돼 있다.
합치려면 그 결정 자체를 다시 논의해야 하므로 자동 수정은 금지, 안건으로만 남긴다.
(이 건은 backend 검토와 main 검토가 서로 모르는 상태에서 같은 지점을 지목해서, 교차 검증이 된 셈이다.)

## 4. 고칠 가치가 큰 것 10건

이득이 큰 순서다. 전부 "겉보기 동작은 그대로 두고 내부 구조만 바꾸는" 리팩토링이고, 기존 테스트 5,359개가 안전망이 된다.

**1. `claudeAgentRun.ts` 를 네 조각으로 나누기** 🔶
1,850줄 한 클래스가 백그라운드 작업 감시, 전송 횟수 회계, 유휴 종료 타이머, 메시지 펌프까지 여섯 가지 일을 한다.
어떤 관심사를 고치든 이 파일이 바뀌는 구조라서 변경 횟수 23회가 나온 것이다.
검토 결과, 위험이 낮은 것부터 네 단계로 떼어낼 수 있고(감시 → 회계 → 타이머 → 나머지), 각 단계마다 기존 골든 테스트가 그대로 합격 기준이 된다.

**2. 멀티 패널의 전송 로직 두 벌을 한 벌로** 🔶
`panelSession.ts` 안에 메시지 전송/중단 로직이 "로컬판"과 "매니저판" 두 벌로 존재한다(약 140줄 × 2, 주석 스스로 "동일한 비즈니스 로직"이라고 적어놨다).
게다가 로컬판은 **실제 앱에서는 안 쓰이고 테스트에서만 쓰인다**는 게 확인됐다.
공용 코어 하나로 합치면 이 파일의 유지비가 크게 준다.

**3. "대화 종료 시 초기화할 필드 목록"을 한 곳으로** 🔶
같은 필드 15개 목록이 세 곳에 복사돼 있고, 코드 주석에 "새 필드를 추가하면 세 곳 다 고쳐야 함, 안 하면 값이 샌다"는 경고가 반복해서 달려 있다.
경고 주석이 반복된다는 것 자체가 구조적 함정이라는 증거다. 목록을 한 곳에 정의하고 세 곳이 그걸 쓰게 바꾼다.

**4. 아무도 안 읽는 `messages` 필드 제거** 🔶
상태 저장소에 `messages`라는 필드가 있는데, 쓰는(기록하는) 코드는 4곳인데 **읽는 코드가 0곳**이라는 게 실측됐다.
과거 구조의 잔재다. 지우면 관련 동기화 코드도 함께 사라진다.

**5. 단일 채팅 ↔ 멀티 패널의 중복 로직 5종을 공유 훅으로** 🔶
자동 스크롤, "작업 중" 표시 계산, 턴 블록 렌더링, 입력 팔레트, 전송 파이프라인 — 다섯 계열이 두 화면에 거의 같은 코드로 두 벌씩 있다(코드 주석이 "동형 이식"이라고 자인한 곳도 있다).
공유 훅/함수로 뽑으면 두 화면의 동작이 어긋나는 버그 자체가 원천 차단된다.

**6. `agentEvents.ts` (1,041줄) 를 주제별로 나누기** 🔶
이벤트 계약 28종이 여섯 주제로 섞여 있어서, 어떤 이벤트를 추가하든 이 파일이 바뀐다.
주제별 파일로 나누고 기존 파일은 재수출(re-export) 통로로 남기면 **import 경로가 하나도 안 바뀐다** — 같은 방식의 선례가 이미 저장소에 있다.
단, 이 파일은 공용 계약이라 계약 골든 테스트 통과가 조건이다.

**7. 모델 이름 목록 세 곳을 타입으로 묶기** 🔶
지원 모델 목록('opus', 'sonnet' 등)이 세 파일에 흩어져 있어서 모델을 하나 추가하면 세 곳+α를 손으로 맞춰야 한다.
목록을 한 곳에 정의하고 나머지를 `Record<KnownModel, …>` 타입으로 조이면, 앞으로 목록이 어긋날 때 **컴파일러가 잡아준다**.

**8. 테스트 셋업 헬퍼 3종 추출** 🔶
SDK 메시지 팩토리가 28개 파일에, `window.api` 목업이 85개 파일에, 스토어 리셋 함수가 14개 파일에 복사돼 있다.
복사본끼리 이미 형태가 어긋나기 시작한 것도 실측됐다.
공용 헬퍼 3개를 만들고 갈아끼우는 작업 — 테스트가 검증하는 *의미*는 절대 바꾸지 않는 조건이다.

**9. 설정 저장소 3형제의 중복 정리** 🔶
commands/skills/mcp 세 설정 모듈이 frontmatter 파서, 비활성 목록 읽고 쓰기, 의존성 주입 보일러플레이트를 각자 한 벌씩 들고 있다. 공용 모듈로 합친다.

**10. `prefs.ts` 와 `profile.ts` 쌍둥이 통합** 🔶
두 파일이 캐시·검증·안전 쓰기까지 같은 골격이다. 제네릭 JSON 파일 저장소 하나로 만들고 각자는 검증 규칙만 주입한다.

**그 외에 사람 확인이 필요한 것 5건** (자동 진행 안 함):
잠재 버그 1건 — `03_lsp/manager.ts:80`의 폴백 로직이 루프 첫 반복에서 무조건 return이라 **두 번째 후보 경로가 영원히 안 돈다**(패키징된 배포 환경에서 문제가 될 수 있음, 고치면 동작이 바뀌므로 의도 확인 필요) / 영속화 코드의 필드 복사 통합(디스크 JSON 형태가 바이트 단위로 같아야 함) / 원자적 파일 쓰기(writeFileAtomic) 도입 여부(헌법에 "미이식"으로 박제된 결정이라 재론 필요) / mcp 정렬의 주석과 코드가 서로 다른 말을 함(어느 쪽이 의도인지 확정 필요) / ARCHITECTURE.md 지도에 없는 main 루트 파일 7개(문서 갱신 안건).

## 5. 건드리면 안 되는 것

**자동 수정 영구 금지 구역** — preload, IPC 핸들러, 권한 판정 코드는 "테스트로는 못 잡는 구멍"이 생길 수 있어서 영원히 사람 전용이다. 이번 진단에서 이 구역 관련 관측 5건은 전부 "보고만" 상태로 남겼다(타입 중복 1, 이름 불일치 2, 위 3장의 ③, IPC 등록 위치 1).

**⚠️ 중복처럼 보이지만 합치면 안 되는 코드 2건** — 이번 진단의 중요한 수확이다:
- 모드 매핑 테이블 3개(`LIVE_MODE_PICKER_TO_SDK` 등)는 겉이 비슷하지만 각각 "라이브 전환용 / 세션 생성용 / 역방향"으로 **의미가 다르다**. 합치면 동작 버그가 된다.
- SDK 메시지 형상과 오케스트레이션 도구 목록을 공용층으로 옮기는 것은 엔진 추상화 위반이다.
다음에 자동 적용 모드로 돌 때 Worker가 이걸 "정리"하겠다고 나서면 막아야 하므로 명시해 둔다.

**눈으로 봐야 하는 것 3건** — 아바타 렌더링 공유, 턴 목록 렌더 통합 등 JSX 구조가 바뀌는 것들은 화면 확인이 필요해서 제안까지만.

## 6. 다음에 자동 검사로 굳히면 좋은 것

리팩토링으로 고친 성질은 그냥 두면 도로 무너진다. 사람이 기억하는 대신 기계 검사로 고정할 후보 3건:

1. 모델 목록 타입 조이기(4장 7번) — 목록 어긋남을 컴파일러가 잡게 됨.
2. 대화 필드 기본값 파생 구조(4장 3번의 발전형) — 필드 누락을 컴파일러가 잡게 됨.
3. **테스트 파일 수 기준선(현재 402개) 기록** — 앞으로 테스트 파일을 통합·개명할 때 실수로 수집에서 빠지면 "테스트가 줄었는데 전부 통과"라는 거짓 초록불이 되는데, 파일 수를 함께 비교하면 이걸 잡는다.

덤으로 하나: `tests/integration/core-loop.test.ts:827`에 문자 그대로의 **NUL 바이트**가 박혀 있어서, 검색 도구(grep)가 이 파일을 바이너리로 오판해 **텍스트 검색에서 조용히 빠지고 있다**. 이스케이프 표기로 바꾸면 검증 의미는 그대로고 검색만 정상화된다.

## 7. 스윕 절차(v3.1) 자체에 대한 피드백

이번 실행은 새 절차의 첫 실전이었고, 절차의 손볼 곳 4건이 실측됐다:

1. 변경 빈도(churn) 측정이 과거의 대량 파일 개명에서 끊긴다 — 측정 구간을 개명 이후로 한정하거나 개명을 반영하는 보정이 필요하다.
2. 절차에 적힌 "크기 경고 훅의 경고 이력을 진단 입력으로 쓴다"는 문장은 실행 불가였다 — 그 훅은 경고를 로그로 남기지 않는다. 문장을 고치거나 훅에 로그를 추가해야 한다.
3. 영역 분담표에서 main 영역이 어댑터 폴더까지 포함하는 것처럼 읽힌다 — "어댑터는 backend 소관"을 표에 명시해야 한다.
4. dry-run에서는 전용 브랜치를 만들 이유가 없다(커밋이 0이므로) — 브랜치 생성은 자동 적용 회차에만 하도록 바꾸는 게 낫다.

잘 작동한 것: codegraph로 "이 코드를 지워도 되나"를 교차 확인하는 흐름(죽은 코드 판정 다수), 검토 에이전트 5기 병렬 실행(마찰 0), 기준선 측정의 위임 실행. 참고로 실행 중 서킷 브레이커의 "도구 호출 100회 누적" 알림이 한 번 떴는데, 차단 없이 알림만 하는 설계대로 동작했다.
