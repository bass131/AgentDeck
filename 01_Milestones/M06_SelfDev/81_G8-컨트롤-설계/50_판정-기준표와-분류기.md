# 50 — 판정 기준표와 `auto` 분류기

사용자 기준을 한 표로 모으고, 표의 각 행을 어떤 노드가 집행하는지 정한다. 결정적인 행은 규칙 노드와 잠금 노드가 집행하고, 판단이 필요한 행은 분류기가 집행한다.

## 기준표 초안

「지금」 칸은 실물이다(`10_현재-컨트롤-실사.md`). 「제안」 칸은 설계 제안이다. 「지금」과 다른 제안에는 **변경**이라고 적었다. 각 행의 최종 판단은 사용자가 정한다.

| 행위 | 지금 | 제안 판단 | 제안 집행 |
|---|---|---|---|
| PR 병합 | 질문(가드, 설정 `ask`) | **변경** 에이전트에게서 뺀다 | 사람 버튼, 잠금 노드 거부(`40`) |
| `master` push | 질문(가드), 서버 거부 | 질문 유지 | 서버가 거부하고 규칙 노드는 질문. 패턴으로는 실제 목적지를 다 가리지 못해 거부로 두면 정당한 작업 브랜치 push까지 막힐 수 있다 |
| 브랜치 보호·ruleset 변경 | 질문(가드 `gh-api-보호설정`) | **변경** 에이전트에게서 뺀다 | 토큰 권한(L0, `40` 단계 B), 잠금 노드 거부 |
| 강제 push, 로컬 브랜치 강제 삭제 | 거부(가드 차단) | 거부 유지 | 규칙 노드 거부, `master`는 서버 거부 |
| 원격 브랜치 삭제 | 질문(가드) | 질문 유지 | 규칙 노드 질문 |
| 릴리스, 패키지 배포·빌드 | 질문(가드, 설정 `ask`) | 질문 유지 | 규칙 노드 질문 |
| `reset --hard`·`clean -f`·`restore`·`checkout --`·`stash drop` | 거부(가드 차단) | 거부 유지. 질문으로 완화할지는 사용자 결정 | 규칙 노드. 분류기 기본 차단 목록에도 있다 |
| `rm -rf`, `Remove-Item -Recurse`, `del /s`, `rmdir /s` | 거부(가드 차단) | 거부 유지. 완화는 사용자 결정 | 규칙 노드 |
| `git config --global` | 거부(가드 차단) | 거부 유지 | 규칙 노드 |
| `curl`·`wget`·PowerShell | 거부(설정 `deny`) | 거부 유지 | 규칙 노드 |
| `.env`·`secrets/` 읽기 | 거부(설정 `deny`) | 거부 유지 | 규칙 노드 |
| 작업 브랜치 push, `gh pr create` | 허용(설정 `allow`) | 허용 유지 | 규칙 노드 허용 |
| 판정 장치 파일 편집 | 편집 계획 게이트, 헌법 3조 규범 | 유지 | 저장소 노드. 계획에 명시됐는지는 기계가 판정할 수 없어 규범으로 남는다(헌법 3조) |
| 앱 엔진·컨트롤 설정 쓰기 | 막는 장치 없음 | **변경** 거부 | 잠금 노드(`30` 보호) |
| 그 밖의 애매한 꼴 | 가드에 안 걸리면 일반 모드는 카드, 앱 `자동`·`Bypass`는 허용 | **변경** 분류기에 맡긴다 | `auto` 분류기와 문장 노드 |

「그 밖의 애매한 꼴」의 예: `eval`, 변수에 담아 만든 명령, heredoc(셸에 여러 줄 입력을 바로 먹이는 `<<EOF` 문법)으로 셸에 넘기는 명령, 처음 보는 스크립트 실행.

공식 문서는 「명시적 ask 규칙은 여전히 질문을 강제한다」, 「거부 규칙은 bypassPermissions를 포함한 모든 모드에서 막는다」고 적는다(https://code.claude.com/docs/en/permission-modes). 그래서 표의 결정적인 행은 분류기보다 먼저 확정된다.

## 분류기 기본값과 사용자 기준이 다른 곳

- 공식 기본 허용 목록에 「작업 중인 저장소의 어느 브랜치로든 push, 기본 브랜치 포함」이 있다. 사용자 기준에서 `master` push는 승인 항목이라, 이 행은 분류기에 맡기지 않는다.
- 공식 기본 차단 목록에는 강제 push, `git reset --hard` 류, 사람이 승인하지 않은 PR 병합, IaC(인프라를 코드로 관리하는 도구) 파괴 명령, 자격 증명 출력이 있다. 이 행들은 규칙 노드와 분류기가 이중으로 막는다. 문장 노드의 `"$defaults"` 고정(`30`)이 이 이중 방어의 전제다.
- `soft_deny`는 「사용자 의도가 풀 수 있는 차단」이고 `hard_deny`는 「사용자 의도로도 풀리지 않는 차단」이다(공개 타입 주석).
- 기본 목록은 릴리스마다 바뀐다. 기준표는 기본 목록에 기대지 않고 사용자 기준을 명시한다.
- 분류기는 사용자 설정 `~/.claude/settings.json`의 `autoMode`도 읽는다(공식 문서 auto-mode-config). 앱은 `settingSources`에 `user`를 넣고 있다. 그래서 에이전트가 그 파일에 허용 문장을 쓰면 분류기가 느슨해진다. 이 파일도 L1 보호 대상에 넣을지 이행 goal에서 정한다.

## 앱 `자동`을 공식 `auto`로 잇기 전에 잴 것

공개 API와 반환값으로만 잰다.

1. `query()`의 `permissionMode: "auto"`로 처음부터 시작할 수 있는가. 재개로 여는 실행에서도 유지되는가.
2. 분류기가 정하지 못한 호출이 `canUseTool`에 어떤 `options`로 오는가. 공개 타입은 그런 호출이 `canUseTool`로 온다고 적는다. 지금 169행은 `자동`이면 그것을 허용한다. 이 분기를 「카드로 올림」으로 바꿔야 하는지가 이 실측으로 정해진다.
3. 분류기가 막은 호출이 SDK 메시지로 어떻게 오는가. 공식 문서는 사유가 보통 `[Data Exfiltration]` 같은 규칙 이름이라고 적는다.
4. 인라인 `autoMode` 블록이 반영되는가. `"$defaults"`를 넣은 목록과 뺀 목록에서 기본 차단(예: 강제 push)이 어떻게 달라지는가.
5. 연속 3번, 누적 20번 차단 뒤 `auto`가 멈추고 질문으로 돌아가는 동작이 SDK 세션에서 어떻게 보이는가.
6. 허용 규칙과 분류기의 관계. 공개 타입의 `autoMode.classifyAllShell`은 「켜면 Bash 허용 규칙을 멈추고 모든 셸 명령을 분류기로 보낸다」다. 그렇다면 기본값에서는 `Bash(node *)`·`Bash(npx playwright*)` 같은 허용 규칙에 걸린 명령이 분류기를 건너뛴다. 이를 확인하고 `classifyAllShell`을 켤지 사용자 결정으로 올린다.
7. 인라인 `permissions.ask`만 걸린 호출(가드와 겹치지 않는 것)이 `auto`·`Bypass`에서 규칙 제안을 달고 오는가. 오면 169행이 카드 없이 허용하므로, 질문은 앱 PreToolUse 콜백으로 낸다(`30`).
8. `blockWritesOutsideWorkingDirectories`를 켰을 때 정당한 쓰기(임시 폴더, 하위 에이전트 산출물)가 막히지 않는가.

## 분류기 모델

- 기본은 Sonnet 5이고 `CLAUDE_CODE_AUTO_MODE_MODEL`로 바꿀 수 있다(공식 문서 permission-modes).
- Haiku 5.5는 공식 문서가 분류용 빠른 모델로 권하고, `auto` 지원 모델 목록에 있다.
- 바꿀지는 실측으로 정한다. G5에서 모은 정답 붙은 명령 자료(실제 세션 명령 3,626건 등)로 두 모델을 돌려 위험한 허용 수와 지연을 비교한다. 자료는 Anthropic API 밖으로 보내지 않는다.
- Jev(TypeSafe의 판별 전용 모델로, 선택지와 확률만 답한다)는 이 자리의 시범 후보로만 남긴다. 외부 전송 범위와 접속 경로는 사용자 결정이다(Second Brain `Jev-도입-검토.md`).

## 문장 노드의 초기 문장 후보

사용자가 GUI에서 고르고 고친다. 각 목록 맨 앞에는 `"$defaults"`가 고정으로 붙는다.

- `environment`: 「Source control: github.com/bass131 아래 저장소」, 「작업 브랜치 push와 PR 생성은 일상 작업이다」.
- `soft_deny`: 「`master`에 닿는 모든 git 쓰기」, 「`.claude/` 판정 장치의 변경」.
- `hard_deny`: 「GitHub 브랜치 보호·ruleset·토큰의 변경」, 「앱 엔진과 컨트롤 설정의 변경」.
