# ADR-005 — 병합 경계는 마일스톤 단위다: goal은 에이전트가, `master`는 사람이 병합한다

- 상태: 채택 · 날짜: 2026-11-18 · 마일스톤: M07 G14(결정), M08 G1(장치)·G2(이 기록)
- 대체: ADR-003 결정 1의 「병합까지 자율」 기각(goal마다 사람이 병합)과 결정 5(goal의 마감 = 사용자의 병합 승인)를 대체한다. ADR-003 결정 1의 경계 — `master`에 들어가는 행위·릴리스·배포·강제 push·브랜치 삭제는 사람 몫 — 는 그대로다. ADR-004 결정 1·2(`master`는 서버가 지키고 가드는 그 위의 이중 안전장치)도 그대로다. ADR-004의 「병합의 사람 판정은 `gh pr merge` 다이얼로그」「CI가 없고」는 M07 G6·G8·G12부터 이미 낡았다.
- 맥락 문서: `01_Milestones/M07_Controls/95_Goal-G14-마일스톤-단위-규칙.md`(헌법 10·11조 개정), `01_Milestones/M08_MilestoneLoop/00_마일스톤-스펙.md`, `10_Goal-G1-병합-길-장치.md`(장치와 CLI 실측 표)
- 판정 근거: M07 G14 결정 대장 [USER] 2026-11-18 「A 마일스톤 단위로 가자」와 「에이전트 병합 거부는 master 병합에만 남긴다: 좋아」, 그 원문을 장치로 옮긴 G14 [AI] 해석(호출은 대상과 관계없이 거부하고 로컬 병합 길을 연다), M08 스펙 결정 대장 [USER] 「1A 2A 3A 4A」·「합의」·「a로」

## 배경

ADR-003 이후 goal 하나가 끝날 때마다 사용자가 `master` 병합을 눌렀다. goal PR마다 사람의 병합 한 번을 기다렸다.
2026-11-18 방향 재정비에서 사용자는 사람이 궁극 목표·기획·Taste와 마일스톤 브레인스토밍만 맡고, 구현과 운영은 에이전트가 끝까지 맡는 쪽을 골랐다.
goal마다 사람을 부르면 그 방향이 서지 않는다. 그래서 사람이 결과를 보는 자리를 마일스톤의 끝 한 번으로 옮겼다.

## 결정

### 1. goal 병합은 에이전트가, `master` 병합은 사람이 한다

마일스톤마다 `master`에서 `milestone/<이름>` 브랜치를 가른다. goal 작업 브랜치는 그 위에서 갈라 PR을 마일스톤 브랜치로 연다.
에이전트는 goal PR을 로컬 `git merge --no-ff`로 마일스톤 브랜치에 합치고 push한다. PR 머리가 base에 닿으므로 GitHub가 PR을 병합됨으로 닫는다.
마일스톤 끝에 에이전트가 마일스톤 브랜치에서 `master`로 PR을 열고 결과 보고를 싣는다. 그 병합은 사람이 한다 — 현황판·앱 PR 카드의 「병합」 버튼, GitHub 웹, 또는 사용자가 직접 치는 `gh pr merge … --match-head-commit`.
릴리스, 패키지 배포, 강제 push, 브랜치 삭제, 보호 설정 변경은 그대로 사람 몫이다.

### 2. 에이전트는 병합 호출을 쓰지 않는다

goal 병합의 길은 로컬 `git merge`뿐이다. `gh pr merge`, REST `pulls/<n>/merge`, GraphQL 병합 변이는 대상 브랜치와 관계없이 쓰지 않는다.
설정의 거부 규칙, 위험 명령 가드, 앱의 잠금 노드 `merge-deny`가 이 호출을 묻지 않고 거부한다. 대상 브랜치를 가려서 열면 판독이 「이 병합이 `master`에 닿는가」를 다시 판정해야 하는데, ADR-003·004가 보인 대로 명령 글자로는 그 판정이 닫히지 않는다.
사용자 원문은 「에이전트 병합 거부는 `master` 병합에만 남긴다」였다. 이 결정은 그 원문을 결과로 지킨다 — 에이전트는 `master`로 병합하지 못하고 마일스톤 브랜치로는 로컬 병합한다. 「호출은 대상과 관계없이 거부」는 수단에 대한 [AI] 해석(G14 결정 대장)이며, 앱에 `master` 한정 잠금을 두는 설계(비전 `60_기존에서-바뀌는-것.md`)를 막지 않는다.
거부 안내 글은 M08 G2에서 맞췄다. CLI 가드의 `MERGE_HINT`는 이 저장소의 두 길(`master`는 사람, goal은 로컬 `git merge --no-ff`)을 말한다. 앱의 `REASON`은 모든 작업 폴더에 붙으므로 중립으로 말한다 — 저장소 규칙이 로컬 병합을 정해 두었으면 그 조건을 따르고, 아니면 PR 생성까지만.

### 3. 병합 조건은 규범이고, 장치는 길만 연다

goal을 병합하는 조건은 셋이다. goal PR의 `hard-gates` 통과, goal 검증 기록의 마지막 줄 `PASS`, 강 등급 goal이면 독립 검수 반영. 마일스톤 브랜치에는 서버 보호와 필수 검사가 없어 이 조건은 규범으로 지킨다(헌법 10조).
장치는 길만 연다(M08 G1). 설정 allow `Bash(git merge --no-ff *)` 한 꼴, `hard-gates` 트리거 `[master, 'milestone/**']`.
CI를 통과한 커밋과 병합하는 커밋을 묶는 것은 정형 절차다. `gh pr view <N> --json headRefOid,statusCheckRollup`으로 머리 SHA와 검사를 읽고, `git fetch` 뒤 `origin/<goal 브랜치>`를 병합하며, 그 SHA가 머리 SHA와 같은지 확인한 뒤 push한다(M08 work-pin).

### 4. 효력 날과 과도기

에이전트의 goal 병합은 장치가 `master`에 들어간 날 효력을 가졌다 — 2026-11-18, PR 88(`525c57ce`)을 사용자가 병합했다.
그 전 과도기에는 goal 브랜치를 `master`에서 갈라 `master`로 PR을 열고 사용자가 병합했다. M08 G1이 그 마지막 goal이다.

## 감수한 것

- 마일스톤 브랜치는 서버가 지키지 않는다. 그 브랜치의 강제 push와 삭제는 가드 한 겹이고, 병합 조건은 규범과 사후 감사(git 이력, 검증 기록)에 기댄다.
- allow `Bash(git merge --no-ff *)`는 `--no-ff` 뒤의 전략 옵션(`-s ours`·`-X theirs`)도 묻지 않는다. `-s ours`면 goal 내용 없는 병합 커밋이 PR을 병합됨으로 닫는다 (M08 Backlog 3).
- 현재 브랜치가 `master`인 채 맨 `git push`·`git push origin HEAD`를 하면 가드도 설정도 묻지 않는다. 같은 뿌리의 꼴이 가드 시험의 「서버 보호에 맡기는 꼴」 묶음에 M04부터 있고, 이 결정의 allow가 `git switch master && git merge --no-ff x && git push` 사슬의 질문 하나를 없앴다. 지금은 공개 저장소의 서버 보호가 거부한다. Free 요금제로 비공개로 돌리면 서버 보호가 사라지므로, 그 전에 막아야 한다 (M08 Backlog 2, G1 CLI 실측 표).
- 사람이 goal마다 diff를 보던 자리가 사라진다. 대신 마일스톤 PR의 결과 보고와 강 등급 goal의 독립 검수가 그 몫을 진다.
