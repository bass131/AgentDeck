## 실사에서 나온 발견

1. **에이전트가 쓰는 토큰으로 서버 보호를 풀 수 있다.**
   - `gh auth status`: 계정 `bass131`, 저장 위치 keyring(Windows 자격 증명 관리자), 범위 `gist`·`read:org`·`repo`·`workflow`.
   - 저장소 소유자의 `repo` 범위 토큰은 브랜치 보호를 바꾸는 API를 부를 수 있다.
   - `master` 보호(읽기 호출): 관리자 포함 강제(`enforce_admins`) 켜짐, 강제 push 꺼짐, 삭제 꺼짐, 필요한 승인 0, 필요한 상태 검사 없음.
   - 보호 해제를 막는 것은 가드 규칙 `gh-api-보호설정`·`gh-api-쓰기`의 글자 판독뿐이다. 에이전트는 `gh auth token`으로 keyring의 토큰을 꺼낼 수도 있다.
2. **가드의 시간 초과는 통과로 떨어진다.** 가드 내부 오류는 차단한다(최상위 `catch`의 `block`). 그런데 `settings.json`의 가드 항목(60행)에 `timeout`이 없어 기본 600초다. 공식 hooks 문서에 따르면 시간 초과된 command 훅은 도구 호출을 막지 않는다.
3. **앱 `자동` 모드는 대부분의 턴에서 공식 분류기를 쓰지 않는다.**
   - `permissionModes.ts:18`에서 `auto`의 시작 값은 `acceptEdits`이고, 실행 중 전환 때만 SDK `auto`다.
   - 실행은 턴 뒤 유휴 3초에 닫히고(`idleCloseGovernor.ts:3`), 다음 전송이 재개로 새 실행을 연다. 실행이 살아 있는 동안의 전송과 자율 턴(최대 100턴)은 같은 실행에 들어간다.
   - 새 실행을 열 때 `auto`를 다시 보내는 경로가 없다(`renderer/src/05_Conversation/state/composer.ts:97-101`). 그래서 대부분의 실행이 `acceptEdits`다.
   - 권한 콜백의 분기 순서(`permissionCoordinator.ts`): `AskUserQuestion` 처리(150~152행) → `Workflow` 게이트(154~161행) → 규칙 제안이 없는 호출은 모드와 상관없이 카드(164~167행) → `자동`·`Bypass`면 허용(169행) → 읽기 도구 허용 → `acceptEdits`의 비편집 도구 허용 → 나머지 카드. 콜백이 보는 모드는 SDK가 보고한 모드로 갱신된다(`claudeAgentRun.ts:292, 546-548`).
   - 이 어긋남은 M05 Backlog 3(「시작 때와 실행 중 전환 때의 모드 매핑이 다르다, M06이 의미를 정한다」)이 넘긴 것이다.
4. **스폰 게이트 `20_plan-gate.cjs`는 배선돼 있지 않다.** 하위 에이전트를 띄우기 전에 계획을 검사하던 훅이다. M03 P4(`0b8bfdf0`, 2026-11-11)에서 역할 게이트를 내리며 `settings.json`에서 빠졌고 파일만 남았다.
5. **병합 승인의 길이 둘이다.** 앱 안 승인 카드(가드 `gh-pr-merge`와 설정 `ask` 규칙 `Bash(gh pr merge*)`가 겹쳐 사유가 빠진다, M06 Backlog 28)와 결정 보드다. 결정 보드는 작업 트리 안 파일이고, 메인 세션이 보드 응답을 읽고 직접 `gh pr merge`를 실행한다. 어느 길이든 병합을 실행하는 것은 에이전트의 Bash다.
6. **엔진 경로로 앱 프로세스에 코드를 넣을 수 있다.**
   - main 프로세스는 실행을 열 때마다 userData(앱 전용 데이터 폴더)의 `engine-config.json`을 읽는다. 활성 SDK 버전이 캐시와 다르면 `userData/engines/<버전>/node_modules/@anthropic-ai/claude-agent-sdk/`의 JS를 `import()`한다(`10_Engine/engineVersions.ts:286-311`, `04_Claude/queryFn.ts:14-18`).
   - userData는 에이전트가 Bash로 쓸 수 있다. 두 곳에 파일을 쓰면 다음 전송에서 그 코드가 main 프로세스 안에서 돈다. 앱 재시작도 필요 없다.
   - 그러면 권한 콜백과 앞으로 만들 앱 노드가 모두 무력해진다. 「실행 중인 앱은 에이전트가 고칠 수 없다」는 전제는 이 경로를 막아야 성립한다.

## 이 실사가 설계에 주는 것

- 저장소 파일의 컨트롤(L2~L3)은 같은 저장소를 편집하는 에이전트가 끌 수 있다.
- 앱 프로세스의 컨트롤은 L1이다. 앱 실행 트리와 작업 트리가 나뉘어 있고(설치본, 또는 G6처럼 빌드본을 따로 띄움) 엔진 경로와 앱 설정 쓰기를 막았을 때만 그렇다. dev 실행으로 같은 트리를 열면 소스 편집이 바로 리로드되어 L2로 떨어진다.
- 서버 컨트롤은 토큰이 허락하는 만큼만 강하다. 지금 토큰은 관리자 일까지 허락한다.
- 그래서 설계의 방향은 셋이다. 판단 지점을 저장소 파일에서 앱 프로세스로 옮긴다. 앱 쪽의 쓰기 경로(엔진·설정)를 막는다. 되돌리기 어려운 행위는 에이전트 자격 증명에서 뺀다.
