# 모델 라우팅 정책 (v2)

- 확정: 2026-08-08 · 판정: 사용자 게이트 (M04 Phase 7 문답) · 등재: M04 Phase 7 실행

## 이 문서가 정하는 것

여러 AI 에이전트가 한 작업을 나눠 맡을 때, 어떤 역할이 어떤 모델을 쓰는지 정한다.
M03에서 임시로 쓰던 「무인 실행은 claude-fable-5 하나로 한다」는 한시 규칙은 이 문서로 승계되고 종료된다.
한시 규칙은 실행 주체를 구분하지 않았지만, 이 정책은 역할별로 모델을 갈라 배정한다.

오케스트레이터는 전역에 하나가 아니라 **프로젝트당 1기**다.
각 작업 프로젝트의 메인 세션이 자기 프로젝트를 목표 도달형 루프(Layer 0 — Goal Based Loop)로 감독하고, 실행 워커와 교차 검수는 그 루프의 하위 계층으로 붙는다.
이 구조의 원 설계 정본은 노션 「Moodie's Agentic Engineering › 00. Architecture Overview」다.
아래 표는 그 원 설계의 원칙 1 — 「메인 세션은 오케스트레이터다 — 실무는 전부 SubAgent에게 위임하고 메인 세션은 흐름 제어와 판단에만 Context를 쓴다」 — 를 모델 배정으로 구체화한 것이다.

## 역할별 모델 배정

| 역할 | 하는 일 | 쓰는 모델 |
| --- | --- | --- |
| 오케스트레이터 (코디네이터) | 작업을 쪼개 워커에게 발행하고, 결과를 감사하고, 사용자 게이트로 올린다 | `claude-fable-5` |
| 리뷰어 (검수·검증 렌즈) | 산출물을 다시 읽고 결함을 찾는다. 최종 판정의 재료를 만든다 | `claude-fable-5` |
| 실행 워커 | 코드를 고치고, 코드를 조사하고, 계획을 세우고, 문서에 결과를 반영한다 | `claude-opus-5` |
| 교차 검수 | 다른 회사의 모델로 같은 산출물을 독립 검사한다 | Codex |

배정의 이유는 두 가지다.
첫째, 감독과 검수는 넓게 보고 의심하는 일이라 판단이 강한 모델에 둔다.
둘째, 실물을 만드는 일은 지시를 그대로 따르는 성실함이 더 중요해서 실행 모델에 둔다.

「실행 워커」에는 쓰기 워커뿐 아니라 읽기 전용 스카우트, 계획 작성, 문서 반영 워커가 전부 들어간다.
표에 없는 새 역할이 생기면 실행 워커로 본다 — 감독이나 검수를 맡기려면 이 문서를 먼저 고친다.

역할은 세션 단위가 아니라 **작업 단위**로 판정한다.
감독·감사·판정 성격의 작업이면 어느 세션이 스폰하든 `claude-fable-5`, 실물을 만드는 실행 성격이면 `claude-opus-5`, 독립 검사면 Codex다.
실행 워커가 자기 안에서 띄우는 하위 에이전트도 같은 기준으로 판정한다 — 부모가 실행 워커라는 이유로 기본 상속에 맡기지 않고, 그 하위 작업의 성격을 보고 모델을 지정한다.

## full ID 원칙

모델을 지정할 때는 짧은 별칭 대신 full ID를 쓴다.
지금 쓰는 full ID는 `claude-fable-5`와 `claude-opus-5` 둘이다.

별칭을 금지하는 이유는 별칭이 가리키는 실체가 시간에 따라 바뀌기 때문이다.
같은 글자가 어제와 오늘 다른 모델을 뜻하면, 무인 실행의 결과가 왜 달라졌는지 나중에 판독할 수 없다.
판독 가능성이 이 저장소의 규율이므로 모델 지정도 판독 가능한 형태여야 한다.

## 영수증으로 기계 검증한다

어떤 모델이 실제로 떴는지는 주장이 아니라 스폰 영수증으로 확인한다.
워커를 띄우면 남는 기록의 `launch.effective.model` 필드가 그 세션이 실제로 쓴 모델이다.
이 값이 정책과 다르면 그 세션의 산출물을 정책 위반으로 다루고, 사유를 검증 기록에 남긴다.

화면에 뜬 문구나 워커의 자기 보고는 근거가 아니다 — 이 저장소의 다른 게이트와 같은 원칙이다.

## 정책을 바꿀 때의 게이트

역할별 배정, full ID 목록, 영수증 검증 가운데 어느 하나라도 바꾸려면 사용자 판정을 받는다.
바뀐 내용은 이 문서를 고치는 것으로 끝나지 않고, 결정 대장에 `[USER]` 줄로 남아야 유효하다.
새 모델이 나와서 full ID를 갈아 끼우는 것도 정책 변경으로 본다.

## 함께 확정된 운용 규칙 셋

아래 셋은 모델 라우팅과 같은 자리에서 확정됐다 (2026-08-08 사용자 판정).
셋 다 목표가 같다 — 산출물이 사람에게 잘 읽히게 하고, 워커가 시킨 범위를 벗어나지 않게 한다.

### 1. 사람용 글은 Claude 초안 뒤에 Codex 개정을 붙인다

보고서와 열람본처럼 사람이 읽는 산출물은 Claude가 초안을 쓰고 Codex가 고쳐 쓰는 2단 파이프라인을 기본 관례로 한다.
근거는 M03 마감 보고의 실증이다 — 같은 내용을 Codex가 판정자 관점으로 다시 쓰자 훨씬 잘 읽혔다.
기계가 다시 읽는 표면인 로그·work-pin·커밋 메시지는 이 관례의 대상이 아니다.

### 2. Opus 계열에 스펙 문법을 적용한다

`claude-opus-5`를 쓰는 자리에는 작업 지시에 `[완료 기준]`과 `[금지·제약]` 두 구획을 명시한다.
할 일만 적으면 워커가 좋은 뜻으로 범위를 넓히는 일이 생기는데, 끝나는 지점과 손대면 안 되는 것을 함께 적으면 그것이 억제된다.
M04의 워커 전 기수가 이 문법으로 스코프를 지킨 것이 실증이다.

### 3. effort는 항상 명시한다

워커나 하위 에이전트를 띄울 때 추론 강도(effort)를 비워 두지 않는다.
비워 두면 모델이 스스로 강도를 고르는데, 같은 종류의 일에서도 결과의 일관성이 흔들린다.
지정 경로의 우선순위는 환경 변수, 에이전트 정의 머리말, 설정 파일 순이다 — 앞의 것이 뒤의 것을 이긴다.
