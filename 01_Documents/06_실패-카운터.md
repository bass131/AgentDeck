# 쟁점 03 — 3회 실패 카운터 설계

**질문 한 문장**: "같은 실패 3회면 에스컬레이션"(02장 검증 4)에서 실패를 **세는 주체**를 세션 기억에서 구조로 옮기는 설계는 무엇인가?

## 왜 지금

- 03장 매핑 표가 이 규칙을 **현재 가장 큰 구멍**으로 지목했다 (현재 P ⚠️ → 목표 G+S).
- F2(파생 값)가 동반 안건이다: "3회"가 네 곳(00장 원칙 6·플로우 ⑤, 02장 검증 4, 03장 행)에 살아서, 카운터 설계가 바뀌면 네 곳을 동시 수정해야 한다.

## 구멍의 해부 — 왜 지금은 P인가

지금 설계에서 3회를 세는 주체는 메인 세션의 기억이다.
Context가 길어지면 세션은 "이번이 몇 번째 실패인지"를 반드시 틀린다 — 03장의 표현으로, 판단 층의 확률적 약속이다.
더 나쁜 점은 실패 방향으로 조용히 깨진다는 것: 카운트를 잊으면 루프가 멈추지 않고 계속 돈다 (fail-open).
무한 루프 방지가 규칙의 존재 이유인데, 그 방지 장치 자체가 무한 루프 쪽으로 새는 구조다.

참고 — 표본(실밸개발자)의 circuit-breaker는 "같은 에러가 60초 안에 5번"을 훅이 세서 **경고**한다.
세는 주체가 코드라는 점은 배울 것이지만, 경고에 그치는 것은 P급 처분이라 우리 목표(차단)와 다르다.

## 설계 공간 — 세 개의 하위 결정

결정 1. **실패 사실을 어디에 남기는가** (거처)
결정 2. **누가 남기는가** (기록 주체)
결정 3. **3회 도달을 누가 판정하고 무엇을 막는가** (판정·강제 주체)

### 방식 A — 기록 원장 + 실측 카운트 (추천)

**카운트를 저장하지 않는다. 기록을 세는 것으로 카운트를 매번 실측한다.**

- 거처: Phase-Steps 문서의 각 Phase 절 말미 「검증 기록」 블록.
  기계가 셀 수 있는 마커 + 사람이 읽는 한 문장:

```
### 검증 기록
- FAIL 2026-08-01T14:02 — DoD 테스트 3/7 실패: parseConfig가 빈 문자열에서 throw. 시도: null 가드 추가.
- FAIL 2026-08-01T14:31 — 동일 테스트 2/7 실패: 가드가 undefined를 못 잡음.
- PASS 2026-08-01T15:10 — 7/7 통과.
```

- 기록 주체: 검증 SubAgent (S — 절차에 "결과 줄 기록"을 실행 단계로 박음).
  핵심 보강: **검증 결과는 문서에 적힌 줄로만 유효하다.**
  다음 단계 게이트는 문서의 PASS 줄만 인정하므로, 기록을 잊으면 전진이 막힌다 — 잊음이 fail-open이 아니라 **fail-closed**로 떨어진다.
- 판정·강제 주체: 구현·수정 SubAgent의 **스폰 게이트** (G).
  스폰 전에 해당 Phase 절의 FAIL 줄을 센다 (`grep -c "^- FAIL"` 급의 기계 연산).
  3 이상이면 스폰을 거부하고 에스컬레이션 절차로 분기한다 — 루프가 물리적으로 못 돈다.
- 에스컬레이션 산출물: FAIL 줄들이 곧 "지금까지의 시도와 실패 원인" — 별도 정리 없이 원장이 보고서 재료다.

이 방식이 기존 규칙들과 맞물리는 지점:

| 기존 규칙                        | 방식 A에서                                    |
| ---------------------------- | ----------------------------------------- |
| 원칙 4 — 문서가 진실의 원천            | 실패 이력이 세션이 아니라 문서에 산다. 세션이 끊겨도 카운트가 남는다   |
| 질문 3 규칙 2 — 파생 값을 적지 않는다     | 저장된 카운터가 없다. 카운트는 매번 기록에서 실측 — 어긋날 사본이 없다 |
| 산출물 1 — 사람 관측성               | 사람이 문서를 열면 몇 번, 왜 실패했는지 그대로 보인다           |
| 격리 규칙 — 기록은 지우지 않는다          | 원장은 append-only. 리셋도 삭제가 아니다 (아래 리셋 규칙)   |

### 방식 B — 저장 카운터 필드

Phase-Steps 문서(또는 frontmatter)에 `fail_count: 2` 필드를 두고 검증 SubAgent가 +1 한다.
03장 승격 경로에 현재 적혀 있는 방식이다.
단점: 카운터가 이력과 별도로 사는 **저장된 파생 값**이다 — +1을 잊으면 fail-open이고, 이력과 어긋나도 신호가 없다.
질문 3 규칙 2("파생 값을 적지 않는다")를 우리 스스로 어기게 된다.

### 방식 C — 별도 기계 상태 파일

`.claude/state/` 급의 기계 파일에 카운트를 쌓는다 (work-pin과 같은 표면).
독자 소유권 지도의 "카운터 = 기계 상태 파일" 배정과는 맞지만, 두 가지가 걸린다:
사람 관측성이 죽고(숨은 파일), 시도 이력(서사)은 결국 문서에 따로 남겨야 해서 거처가 이원화된다.
방식 A는 "판정용 숫자"를 아예 저장하지 않으므로 이 배정과 충돌하지 않는다 — 저장되는 것은 기록(문서 표면)뿐이다.

## 부속 결정

- **"같은 실패"의 단위**: Phase 단위 누적 3회로 제안한다.
  02장 문구("같은 구간에서")와 정합하고, 에러 시그니처 비교는 판단 층 연산이라 게이트에 못 박는다.
- **리셋 규칙 — 기준점 이동 방식**: 에스컬레이션 후 사용자가 방향을 주면 그 지시를 원장에 `USER-INPUT` 줄로 기록한다.
  게이트는 **마지막 USER-INPUT 줄 이후의 FAIL만 센다** — 카운트는 자동으로 0부터 다시 시작하되, 이전 이력은 지워지지 않는다.
  리셋이 삭제가 아니라 기준점 이동이므로 격리 규칙(기록 보존)과 정합한다.
- **"3" 값의 소유**: 규범에서는 02장 검증 4가 소유한다.
  실물 게이트 코드에 3이 들어가는 것은 인스턴스의 집행 사본이라 허용 — 어긋남은 harness-review 대조 단계의 몫.
