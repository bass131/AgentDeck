# 40 — 병합을 사용자 전용으로 분리

사용자 결정: 「PR 생성까지만 권한을 주고, Merge 권한은 주지않돼, … 사용자만 컨트롤 할 수 있는 결정론적 기능으로 분화」(G8 결정 대장 [USER] 2026-11-17).
이 문서는 그 결정을 GitHub 권한 구조 위에서 실현하는 방법을 정한다. 근거는 GitHub 공식 문서이고, 하위 에이전트가 2026-11-17에 읽어 요약했다. 인용은 그 요약을 거친 것이다. 확인하지 못한 것은 「미확인」으로 적는다.

용어 셋을 먼저 풀어 둔다.
- **fine-grained 토큰**: 저장소와 권한 항목을 골라 만드는 GitHub 개인 접근 토큰이다. 지금 쓰는 `gh` 로그인 토큰(`repo` 범위)은 소유자의 모든 저장소 권한을 갖는다.
- **ruleset**: 브랜치에 거는 GitHub 서버 규칙 묶음이다. 기존 브랜치 보호와 겹쳐 걸리고, 「우회할 수 있는 대상」 목록을 둔다.
- **GitHub App**: 사람 계정과 별개인 GitHub 신원이다. 저장소에 설치하면 정한 권한만 가진 짧은 수명의 설치 토큰을 받는다.

## GitHub 권한의 사실

| 행위 | fine-grained 토큰에 필요한 저장소 권한 |
|---|---|
| 브랜치 push | Contents 쓰기 |
| PR 생성 | Pull requests 쓰기 |
| PR 병합(`PUT /repos/{o}/{r}/pulls/{n}/merge`) | **Contents 쓰기** |
| 브랜치 보호·ruleset 변경 | Administration 쓰기 |

출처: https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens

- **push와 병합은 같은 권한이다.** 토큰 권한만으로는 「push와 PR 생성은 되고 병합은 안 됨」을 만들 수 없다.
- **보호 변경은 토큰에서 뺄 수 있다.** Administration을 주지 않으면 서버가 거부한다. 같은 문서다.
- **토큰은 주인의 능력을 넘지 않는다.** 「토큰은 사용자에게 추가 접근 능력을 줄 수 없다」(https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).
- **같은 신원으로는 서버에서도 못 가른다.**
  - 개인 저장소에서는 소유자만 「승인 없이 보호된 브랜치에 병합」할 수 있다(https://docs.github.com/en/account-and-profile/reference/permission-levels-for-a-personal-account-repository).
  - 「누가 push할 수 있나 제한」은 조직 저장소에만 있다(https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
  - 「PR 작성자는 자기 PR을 승인할 수 없다」(https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews). 그래서 승인 1건을 강제하면 소유자 혼자서는 아무것도 병합하지 못한다. 분리가 아니라 교착이다.
- **신원을 나누면 길이 있다.**
  - ruleset의 「Restrict updates」는 「우회 권한이 있는 사용자만 일치하는 브랜치에 push할 수 있다」(https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
  - 우회 대상으로 저장소 관리자 역할과 GitHub App을 지정할 수 있다(https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository).
  - GitHub App은 개인 계정에도 설치할 수 있고 저장소를 골라 줄 수 있다(https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party).
- **미확인 둘.** PR 병합이 「Restrict updates」의 갱신으로 세어져 막히는지는 문서에 없다. 개인 저장소에서 저장소 관리자 역할 우회가 되는지는 추론일 뿐이다.

이 저장소의 실측(2026-11-17): 공개 저장소다. ruleset 목록 API가 응답했고 ruleset은 0개다. 이 기계의 git 자격 증명 도우미는 `gh auth git-credential`이다. 그래서 `git push`도 `gh`가 고른 토큰으로 나간다.

## 분리의 세 단계

한 번에 L0으로 가지 않는다. 앞 단계마다 쓸모가 있고, 뒤 단계는 GitHub 설정 변경이라 사용자 몫이다(헌법 9·10조).

### 단계 A — 병합 버튼과 에이전트 쪽 거부 (실수 방지, L3)

- **병합 버튼(코드 노드, 사람 버튼)**
  - 앱의 PR 카드에 「병합」 버튼을 둔다. 앱 밖 CLI 세션에서 만든 PR도 같은 카드로 불러올 수 있게 한다.
  - 누르면 앱 main 프로세스가 GitHub에서 PR의 머리 SHA(커밋 해시)를 직접 읽어 화면에 보이고, 병합 API에 그 SHA를 고정해 부른다. 사람이 본 커밋과 병합되는 커밋이 다르면 서버가 거부한다. 근거는 REST 병합 API의 `sha` 매개변수(https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)이고, 이 goal에서 원문은 확인하지 않았다(미확인).
  - 병합 전 결정적 검사는 GitHub 필수 상태 검사로 한다. 하드 게이트 다섯 종을 CI(GitHub Actions)로 돌리고 `master` 보호의 필수 검사로 건다. 이 검사는 서버가 PR 머리 SHA에서 돌린 결과라, 에이전트가 쓰는 PASS 줄과 달리 에이전트가 꾸밀 수 없다. 지금은 워크플로가 없고 필수 검사도 없다. 그래서 CI 도입이 버튼의 앞선 조건이다(`60`).
  - 버튼이 쓰는 자격 증명은 사람의 기존 `gh` 로그인이다. 단계 B에서 바뀐다.
  - 기록의 정본은 앱 노드 기록이다. 병합 뒤 goal 문서는 `master`에 있어 바로 고칠 수 없다. 그래서 다음 종결 커밋에서 노드 기록을 결정 대장의 `[USER]` 줄로 옮겨 적는다.
- **에이전트 쪽 거부(잠금 노드)**
  - 앱 세션에서 `gh pr merge`와 병합 API 경로가 든 `gh api` 호출을 거부한다. 질문이 아니라 거부다. 병합의 길이 버튼이니 에이전트가 물을 이유가 없다.
- **CLI 세션은 따로 바꿔야 한다.** 저장소의 가드(`gh-pr-merge` 질문)와 설정 `ask` 규칙 `Bash(gh pr merge*)`가 남아 있으면 CLI 세션의 에이전트는 승인 뒤 병합할 수 있다. 헌법 10조와 work-pin도 「병합 승인은 결정 보드로」라고 적는다. 그래서 단계 A의 goal에는 판정 장치 단계가 들어간다. 저장소 설정의 `ask`를 `deny`로 바꾸고, 헌법 10조와 `AGENTS.md`, pin의 문구를 「병합은 앱의 병합 버튼으로」로 고친다.
- **얻는 것**: 결정 보드를 거쳐 메인 세션이 대신 병합하던 길이 없어진다. 병합이 사람 손의 결정론적 기능이 된다. M06 Backlog 28(병합 카드에 사유가 없음)은 병합 카드가 사라져 닫힌다.
- **남는 것**: 같은 토큰이라 에이전트가 글자를 바꿔 병합 API를 부르면 서버는 받는다.

### 단계 B — 에이전트 자격 증명 바꾸기 (보호 해제를 L0으로)

- 앱이 세션 환경에 `GH_TOKEN`을 넣는다. 값은 사용자가 만든 fine-grained 토큰이다. 이 저장소만, Contents 쓰기, Pull requests 쓰기, Metadata 읽기를 주고 Administration은 주지 않는다. 이 토큰으로는 보호와 ruleset을 바꿀 수 없다.
- 그런데 사람의 `gh` 로그인(`repo` 범위)이 keyring에 남아 있으면, 에이전트가 `GH_TOKEN`을 비우고 그 토큰을 쓸 수 있다. 그래서 단계 B는 keyring의 사람 로그인을 지우는 것까지다. 그러면 병합 버튼의 자격 증명도 바뀌어야 한다. 버튼을 누를 때마다 기기 인증으로 짧은 수명의 사람 토큰을 받고, 디스크에 저장하지 않는다.
- 이 단계 뒤에는 보호 해제가 L0이다. 병합은 여전히 같은 Contents 쓰기라 서버 차원에서는 막히지 않는다. 다만 에이전트가 쓰는 토큰이 사람 토큰과 달라져, 병합 기록에서 누가 했는지가 갈린다.
- 사용자가 CLI에서 `gh`를 쓰는 습관이 바뀐다. 사람용 로그인은 필요할 때만 받는다. 이것이 사용자 결정 항목이다.
- **잴 것**: `git push`가 `GH_TOKEN`으로 나가는가(자격 증명 도우미 경유). Administration 없는 토큰으로 보호 변경 호출이 거부되는가.

### 단계 C — 신원 분리 (병합을 L0으로, 실측 뒤)

- 에이전트는 GitHub App 신원으로 일한다. App 권한은 Contents 쓰기, Pull requests 쓰기, Metadata 읽기이고, Administration은 없다.
- `master`에 ruleset을 둔다. 「Restrict updates」와 「Require a pull request」를 켜고, 우회 대상은 저장소 관리자 역할(사람) 하나다.
- **먼저 잴 것 셋**
  - App 신원으로 병합 API를 불러 거부되는가. 미확인 1을 푼다.
  - 개인 저장소에서 관리자 역할 우회로 사람의 병합이 되는가. 미확인 2를 푼다.
  - App 설치 토큰의 갱신을 앱이 어떻게 맡는가. App 개인 키를 디스크에 두면 다시 L1이다.
- 실측은 사용자가 GitHub 설정(App 생성·설치, ruleset)을 바꾼 뒤에만 한다.
