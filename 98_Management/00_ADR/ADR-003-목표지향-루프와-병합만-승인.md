# ADR-003 — 목표지향 루프와 「병합만 승인」 경계

- 상태: 채택 · 날짜: 2026-11-13 · 마일스톤: M04 Goal Loop
- 맥락 문서: `01_Milestones/M04_Goal_Loop/00_Goal.md` (결정 대장·실측·검증 기록), `01_개정-문안.md` (집행 문면)
- 판정 근거: M04 결정 대장 [USER] 2026-11-13 — goal 합의 문답 안건 1~4, 그리고 검수 불통과 뒤의 두 문답

## 배경

M03까지의 하네스는 계획을 Phase와 Step으로 나누고, 계획 승인·Phase 착수·마감에서 각각 사용자 판정을 받았습니다.
M03의 승인 문답은 안건이 열 개였고, 마일스톤 종결에 「마감 승인」이 따로 있었습니다.
push와 PR 생성은 설정의 `ask`와 위험 명령 가드가 두 겹으로 승인 다이얼로그를 띄웠습니다.

사용자는 2026-11-13에 이 구조가 불편하다고 밝혔습니다.
에이전트가 직접 할 수 있는 일에서 수행 의도나 허락을 묻느라 멈추는 일이 많다는 것입니다.
원하는 방식은 기획과 목표를 먼저 상의하면 그것을 목표로 삼아 검증과 최종 결과까지 수행하는 목표지향 루프입니다.

## 결정

### 1. 승인 경계는 「병합만 승인」이고, push는 승인 창을 남긴다

합의한 경계는 이렇습니다. 작업 브랜치의 커밋·push·PR 생성은 에이전트의 일이고, `master`에 들어가는 행위(PR 병합, 직접 push), 릴리스, 패키지 배포, 강제 push, 브랜치 삭제는 승인을 받습니다.

집행은 그 경계보다 한 칸 좁습니다. 커밋과 PR 생성은 승인 창 없이 되고, push는 작업 브랜치로 가는 것도 승인 창이 뜹니다.
작업 브랜치 push를 창 없이 통과시키는 장치를 만들지 못했기 때문입니다 (결정 2).

버린 쪽은 「병합까지 자율」입니다. 사용자가 고르지 않았고 이유는 말하지 않았습니다.
`master`는 되돌리기 어려운 공유 상태이고 사람이 결과를 보는 마지막 자리라는 점에서 경계로 남길 값이 있습니다.

### 2. push의 무질의 통과는 만들지 않는다

가드는 모든 push에 질의를 내고, 설정은 `Bash(git push*)`를 `ask`에 둡니다. 가드는 어떤 명령에도 명시적 통과(`permissionDecision: "allow"`)를 내지 않습니다.
PR 생성은 설정의 `allow`(`gh pr create*`)가 열고 가드는 관여하지 않습니다.

작업 브랜치 push만 창 없이 통과시키는 가드를 네 가지 설계로 만들었고, 구현 문맥 없는 검수자가 여섯 번 모두 불통과시켰습니다. 검증 기록의 FAIL 여섯 줄이 그 기록입니다.

- 첫째 설계 — 설정이 push를 `allow`로 열고 가드가 위험한 꼴(`--delete`, `master` refspec)을 골라 잡았습니다. 1차 검수가 목록 밖의 `master` push를 실측했습니다. 축약 옵션, `heads/master`, 같은 줄의 `checkout master` 뒤 push입니다.
- 둘째 설계 — 옵션과 refspec의 허용 목록이었습니다. 2차 검수가 `git push origin 2>&1 master`, `git push>/dev/null origin master`, 아포스트로피가 든 주석 줄 뒤의 push로 뚫었습니다. 가드의 토크나이저는 셸 어휘 분석기가 아닌데 통과 판정이 그 토큰을 믿었습니다.
- 셋째 설계 — 명령 원문 전체가 정규식 한 줄과 맞을 때만 통과를 냈습니다. 명령 판독은 이후 뚫리지 않았습니다. 3차 검수는 저장소 상태를 가드가 `.git`의 파일에서 직접 읽던 부분을 불통과시켰습니다. git 설정의 점 표기 섹션, 한 줄 표기, 줄 연속, 훅 환경의 `GIT_DIR` 류입니다.
- 넷째 설계 — 사용자 판정(「git에게 물어 재구현」)으로 저장소 상태를 `git rev-parse`·`git config --get-regexp`·`git for-each-ref`에게 물었습니다. 4차는 빈 URL 한 줄인 원격(git이 옛 형식 파일을 따른다)과 `HEAD`라는 이름의 ref를, 5차는 pre-push 훅·서브모듈 동반 push·기본형이 아닌 fetch refspec·전송 명령 설정을, 6차는 추적 ref가 symref이거나 정션일 때 push 뒤 로컬 `master`가 덮이는 것을 찾았습니다.

4~6차의 발견은 전부 미리 조작된 저장소 상태가 필요했고 이 PC의 실제 상태에서는 재현되지 않았습니다. 6차는 원격 `master`로 가는 입력을 찾지 못했습니다.
그래도 검수마다 새 조건이 나왔고 수렴한다는 증거가 없었습니다. `git push` 한 줄이 실제로 무엇을 어디에 쓰는지는 명령 문자열과 저장소 상태 몇 가지로 닫히지 않습니다.
사용자는 여섯 번째 불통과 뒤에 이 기능을 Claude Code 하네스에서 빼고, AgentDeck의 커스텀 에이전트를 만들 때 넣을 기능으로 넘겼습니다 (결정 대장 [USER] 2026-11-13, M04 Backlog 7번).

남긴 것이 있습니다.

- 훅의 `ask`는 설정의 `allow` 규칙보다 우선합니다. 문서에서는 직접 확인하지 못했고 실측했습니다. `git branch -d` 프로브(설정 `allow`의 `git branch*`와 가드의 질의)에서 승인 창이 떴다고 사용자가 답했습니다 (검증 기록 USER-INPUT 19:33:04).
- 설정의 `allow`에 `git switch -c*`를 넣어 작업 브랜치 생성의 확인 창을 없앴습니다. `git checkout -b*`는 `-f`가 붙으면 미커밋 편집을 버리므로 넣지 않았고, 같은 이유로 `git switch`의 `--discard-changes`·`-f`는 가드가 차단합니다 (독립 검수 실측).
- 브랜치 삭제(`git branch -d`, `git update-ref -d`, `gh pr close --delete-branch`)와 `git send-pack`이 가드의 질의 대상에 들어갔습니다.

감수한 것도 있습니다.

- goal마다 push에서 승인 창이 한 번 뜹니다. 무인으로 끝까지 가는 루프는 되지 않습니다.
- 가드의 질의는 권한 창을 생략하는 권한 모드에서는 창이 아닙니다. 승인 항목의 집행이 세션의 권한 모드에 기댑니다 (Backlog 6번).
- 설정의 `Bash(node *)`·`Bash(git log*)` 류 허용은 가드를 거치지 않고 git을 띄우거나 `.git` 아래에 파일을 쓰는 길을 열어 둡니다. M04 이전부터 있던 구멍이고 헌법 8조가 규범으로만 막습니다 (Backlog 5번).

### 3. 계획의 기본 형식은 goal 한 장이고 판정부는 고치지 않는다

실측 결과 계획 판정부는 `## 목표`, Phase 머리줄 하나, 그 절의 「검증 기록」, `## 결정 대장`만 요구합니다.
goal 한 장에 Phase 머리줄 한 줄을 남기면 훅을 고치지 않고 통과합니다.

버린 쪽은 판정부를 goal 전용 형식으로 개조하는 안입니다.
판정 모듈과 테스트 네 개, 픽스처 스물여 개를 고쳐야 하고, 얻는 것은 머리줄 한 줄의 제거뿐입니다.
Phase-Steps 다중 파일 형식은 큰 작업용으로 남습니다.

### 4. 독립 검수는 강 등급에만 둔다

강 등급은 판정 장치 변경, 앱 소스 50줄 이상 변경, 애매한 경우입니다.
약 등급은 diff 실사와 하드 게이트, 관련 테스트로 갈음합니다.

버린 쪽은 모든 goal에 독립 검수자를 두는 안입니다.
작은 수정에도 새 검수자를 띄우는 고정 비용이 되돌이의 원인이었다는 진단을 따랐습니다. 그 진단은 다른 저장소(Dawnholder)의 것이고 원문은 사용자의 Second Brain 노트에 있습니다.
감수하는 위험은 약 등급으로 분류된 변경의 결함을 놓치는 것이며, 「애매하면 강」이 그 완충입니다.
이 마일스톤이 강 등급의 값을 보였습니다. 하드 게이트와 자체 테스트를 전부 통과한 가드를 독립 검수가 여섯 번 불통과시켰습니다.

### 5. 마감 승인은 병합 승인이 겸한다

goal의 끝은 PR 생성과 결과 보고입니다. 사용자의 병합 승인 한 번이 마감 판정입니다.
병합 승인은 `gh pr merge`의 승인 다이얼로그입니다. 한 goal의 사용자 입력은 합의, push 승인 창, 그 다이얼로그 셋이 됩니다.
