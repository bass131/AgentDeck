# Backlog — 나중에 고칠지 판단할 내역 (M03)

작업 중에 발견됐지만 그 자리에서 고치지 않기로 한 항목을 모아 두는 표면입니다.
근거는 Preview 제약 절의 「계획 밖 변경 금지 — 발견은 Backlog 보고」 규율입니다.
M02에서 이월된 항목의 정본은 `01_Milestones/M02_Hardening/99_Backlog.md`이고, 이 파일은 M03에서 새로 나온 것만 담습니다.
항목을 실제로 고칠지, 언제 고칠지는 사용자가 정합니다.

## 대기 항목

1. **`plan-record-header.test.mjs`의 실계획 회귀 불변식이 M02 계획을 고정한다** (Phase 1 Step 5 관찰, 2026-11-11) — `.claude/hooks/plan-record-header.test.mjs` 69줄의 PR-06은 「실계획 파일 구획은 통과한다」를 검사하면서 경로를 `01_Milestones/M02_Hardening/_MilestonePreview.md`로 못박습니다. 포인터가 M03으로 옮겨진 뒤에도 이 케이스는 종결된 M02 계획만 보므로, 현재 계획이 규격을 깨도 이 테스트는 green입니다. 지금 green이고 M02 폴더는 역사 표면으로 보존되므로 이 Phase에서는 고치지 않았습니다. 고친다면 `gate-config.json`의 `planPath`를 읽어 현재 계획을 대상으로 삼는 쪽입니다.
2. **하드 게이트 통과는 훅이 강제하지 않는다** (계획 단계 관찰, 2026-11-10 · `00_분류표.md` 6조) — 헌법 6조의 하드 게이트 다섯 종은 `/gate` 커맨드의 규범이고, `git commit`은 허용 목록에 있어 게이트를 돌리지 않은 커밋을 기계가 막지 않습니다. 새는 사례가 관측되지 않아 M03에서는 강제를 더하지 않고 관찰로만 둡니다.
3. **Green 채집이 통하는 `npm test` 형태가 사실상 하나뿐이다** (Phase 2 관찰, 2026-11-11 · M02 Backlog 6의 연장) — tdd-guard의 Green 채집은 파이프·리다이렉트가 섞이면 「판정 불능」이고(M02 Backlog 6), 파이프를 떼도 기본 리포터와 `--reporter=dot`은 출력이 너무 커서 도구 응답이 파일로 떨어지고 `Test Files … passed` 요약 줄이 사라져 역시 「판정 불능」이 됩니다. 이 Phase에서 실제로 통한 형태는 `npm test -- --no-color --reporter=dot`(파이프 없음) 하나였고, 그 전에 `npm test 2>&1 | tail -40`과 `npm test -- --reporter=dot`이 각각 판정 불능으로 기록됐습니다(hook-log 06:27:29·06:28:42). 안내를 어디에 둘지는 M02 Backlog 6과 같은 미결 사안이라 이 Phase에서는 고치지 않았습니다.
4. **하네스 수리에서 TDD 휴리스틱의 3회 임계가 자주 걸린다** (Phase 2 관찰, 2026-11-11) — 훅 소스 한 벌을 고치는 데 보통 세 파일 이상을 연달아 손대는데, 미동반 연속 카운터는 테스트 파일 편집이나 full vitest Green으로만 리셋됩니다. 이 Phase에서 3회째 편집이 두 번 차단돼 56초짜리 전체 스위트를 두 번 돌렸습니다(06:29:02·06:40:48). 휴리스틱의 존폐는 2026-09-18 미결 사안이라 손대지 않았고, 테스트 경로 인정에 `.claude/hooks/_lib/*.cjs`를 더하는 것도 계획 밖이라 하지 않았습니다.
5. **문서 두 곳이 Phase 2의 신설을 반영하지 않는다** (Phase 2 관찰, 2026-11-11) — ① 이 폴더 `00_분류표.md`의 「훅 아홉 종」 표는 `31_edit-plan-gate.cjs` 신설로 열 종이 됐지만 계획 문서라 고치지 않았습니다. ② M02의 사람용 정본 `01_Milestones/M02_Hardening/02_동등성-기준표.md`는 기계 표에 새로 오른 여덟 행(GR-06·07 · WR-01~03 · OK-07~09)을 담지 않습니다 — 종결된 마일스톤 문서라 고치지 않았습니다. 기계 표와 사람용 표의 id·기대 판정을 같게 두는 규약이 `cmd-guard-equivalence.test.mjs` 머리말에 있으니, 정본을 어디로 옮길지 판단이 필요합니다.
6. **실패-카운터 거부 문면이 바뀌었다** (Phase 2 관찰, 2026-11-11) — 판정부를 `_lib/plan-verdict.cjs`로 추출하면서 판정 ②의 거부 문장을 「스폰 거부, 에스컬레이션으로 분기하라」에서 「전진 차단, 에스컬레이션으로 분기하라」로 고쳤습니다. 같은 문장이 이제 스폰 자리와 편집 자리 양쪽에 나가므로 「스폰」이라는 말이 편집 거부에서는 틀린 안내가 됩니다. 이 문장을 단정하는 테스트는 없어 회귀는 아니지만, 계획이 지시한 범위(추출) 밖의 문면 변경이라 관찰로 남깁니다.
7. **라우팅 정책의 역사 서술 세 줄에 옛 ID가 남는다** (Phase 3 관찰, 2026-11-11) — Phase 3 DoD는 「`.claude/`와 `00_Documents/02_Rules/`에 옛 ID가 남지 않는다」인데, `00_Documents/02_Rules/02_모델-라우팅-정책.md` 9·96·97줄은 2026-08-08 한시 규칙과 v2 승계를 서술하면서 `claude-fable-5`·`claude-opus-5`를 인용합니다. 세 줄을 새 ID로 덮으면 2026-08-08에 내려지지 않은 결정을 그 날짜의 결정으로 바꿔 쓰게 되므로 고치지 않았고, 대신 101줄에 「이 ID는 개정 전 값이고 현행 정본은 표와 full ID 원칙 절이다」를 명시했습니다. 운용 표면(배정 표·작업 단위 판정·full ID 목록·스펙 문법 절·승계 절의 메인 세션 줄)은 전부 새 ID입니다. 역사 서술을 어떻게 다룰지는 사용자 판단입니다 — 그대로 두기, 날짜 각주로 분리하기, 승계 절을 ADR로 옮기기 가운데 하나입니다.
8. **리뷰어 정의의 예시 full ID가 앱의 모델 목록과 갈라졌다** (Phase 3 관찰, 2026-11-11) — Phase 3 Step 4의 지시대로 `.claude/agents/reviewer.md` 32줄의 예시를 `claude-opus-5-5`로 바꿨지만, 그 줄이 가리키는 앱의 `02_Project/00_Source/shared/knownModels.ts`는 아직 `claude-opus-5`·`claude-fable-5`·`claude-sonnet-5`·`claude-haiku-4-5`만 압니다. 앱 소스는 이 마일스톤에서 불변이라(제약 「하네스와 앱을 섞지 않는다」) 고치지 않았습니다. 리뷰어가 이 줄을 읽고 앱 코드에서 `claude-opus-5-5`를 찾으면 없습니다 — 앱의 SDK·모델 목록 갱신 마일스톤에서 함께 맞춰야 합니다.
9. **정책 문서의 버전 번호가 제목에서 갱신되지 않았다** (Phase 3 관찰, 2026-11-11) — 라우팅 정책의 제목은 아직 「모델 라우팅 정책 (v2)」입니다. 배정 표에 역할 한 종이 늘고 full ID 셋이 바뀐 것은 v3에 해당할 만한 변경이지만, 버전 번호 체계를 바꾸는 것은 계획이 지시한 범위 밖이라 4줄에 개정 줄만 더했습니다.
10. **effort 값이 정책 문서에 없고 에이전트 정의에만 있다** (Phase 3 관찰, 2026-11-11) — 결정 대장 [USER] 2026-11-11은 실행 워커와 리뷰어의 effort를 `high`로 정했고 두 정의 파일이 그 값을 듭니다. 그런데 정책의 「3. effort는 항상 명시한다」 절은 지정 경로의 우선순위만 적고 역할별 값은 적지 않아, 정책만 읽은 사람은 승인값을 알 수 없습니다. 그 절의 문장은 이 Phase에서 바꾸지 않기로 돼 있어 손대지 않았습니다 — 배정 표에 effort 열을 더할지는 사용자 판단입니다.
