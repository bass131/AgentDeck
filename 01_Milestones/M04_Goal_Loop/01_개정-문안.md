## 10조 — 교체

제목과 본문을 아래로 바꾼다.

> ### 10. `master`에 들어가는 행위는 사용자 승인 게이트다
>
> 작업 브랜치의 커밋, 작업 브랜치 push, PR 생성은 에이전트가 승인 없이 합니다.
> PR 병합, `master` 직접 push, 릴리스, 패키지 배포, 강제 push, 브랜치 삭제는 사용자 승인을 받습니다.
> 위험 명령 가드가 승인 다이얼로그로 잡으며, 그 다이얼로그를 우회하는 방법을 찾는 것은 금지입니다.
> `master` 위에서 직접 작업하지 않습니다 — goal마다 작업 브랜치를 먼저 만듭니다.
> 근거는 M04 결정 대장 [USER] 줄입니다.

## 11조 — 신설

> ### 11. 합의된 goal은 끝까지 간다
>
> goal은 한 장이며 범위를 네 항목으로 씁니다 — 만들 것, 건드릴 곳, 하지 않을 것, 관찰 가능한 완료조건.
> 사용자와 goal을 합의한 뒤에는 구현, 검증, 커밋, push, PR 생성, 결과 보고까지 멈추지 않습니다.
> 멈추는 곳은 넷뿐입니다 — goal 합의, 완료조건이나 범위를 바꿔야 할 때, 7조의 FAIL 세 번, 10조의 승인 항목.
> 이미 받은 승인을 다시 묻지 않습니다. 실행 단계의 목록은 goal 합의 때 한 번 승인받습니다.
> 완료조건 밖의 새 아이디어는 Backlog에 한 줄로 남기고 승인을 묻지 않습니다. 애매하면 범위 밖입니다.
> 루프는 완료조건을 막는 범위 안 결함만 고칩니다. 이번 변경과 무관한 기존 실패는 밖으로 분리하되 결과 보고에 공개합니다.
> goal의 마감 판정은 병합 승인이 겸합니다. goal이 끝나면 다음 goal을 자동으로 시작하지 않습니다.

## `settings.json` 승인 규칙 변경안

- `ask`에서 `Bash(git push*)`와 `Bash(gh pr create*)`를 빼고 `allow`에 넣는다.
- `ask`에 남는 것은 `Bash(gh pr merge*)`, `Bash(gh release*)`, `Bash(npm publish*)`, `Bash(npm run package*)`다.
- `allow`의 `git push*`는 `master` 향 push와 강제 push까지 문자열로는 포함한다. 그 둘을 가르는 것은 아래 가드 규칙의 몫이다.
- `allow`에 `Bash(git switch -c*)`와 `Bash(git checkout -b*)`를 넣어 작업 브랜치 생성의 확인 창을 없앤다.

## 위험 명령 가드 규칙 변경안

- `git-push` 규칙을 좁힌다 — `ask` 대상은 `master`·`main`을 향한 push(명시 refspec, 또는 refspec 없이 현재 브랜치가 `master`인 경우), 원격 브랜치 삭제(`--delete`, `:브랜치`), `--all`·`--mirror`다. 그 밖의 작업 브랜치 push는 통과한다.
- 현재 브랜치는 `.git/HEAD`를 읽어 판정한다. 읽지 못하면 `ask`다 (fail-closed).
- `gh-pr` 규칙은 `merge`만 `ask`로 남기고 `create`는 통과한다.
- 강제 push, `git branch -D`, `gh release`, `npm publish`, `npm run package` 규칙은 그대로 둔다.
- 병합 안 된 브랜치가 아니어도 지우는 `git branch -d`를 `ask` 대상에 넣는다 (브랜치 삭제는 승인 항목).
- 함께 고칠 테스트는 `dangerous-cmd-guard.test.mjs`, `cmd-guard-equivalence.test.mjs`, `cmd-guard-surface.test.mjs`다. 따옴표 판독부는 건드리지 않는다.
