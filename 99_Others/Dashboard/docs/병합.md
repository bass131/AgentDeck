# 현황판 병합 — 병합 카드, 사람 확인 창, 머리 SHA 고정

현황판에서 병합 대기 PR을 보고 「병합」을 눌러 병합한다(M07 G9, 2026-11-18). 병합은 서버가 띄우는 Windows 확인 창에서 사람이 「병합」을 눌러야만 나가고, 화면에 보인 머리 SHA로 고정된다.
앱 PR 카드(G8, `02_Project/00_Source/main/08_Git/prMerge.ts`)와 같은 판정을 빌드 없는 `.mjs`로 옮겼다. 두 구현은 모듈을 나눠 쓰지 않고, `test/merge.test.mjs`가 앱 `prMerge.test.ts`의 사례 표를 그대로 옮겨 같은 응답 꼴을 맞춘다.

## 화면 — 병합 카드

- 자리는 「결정 요청」 밑, 「내 손이 필요한 일」 위의 자기 영역(`#merge`)이다. 「지금」의 초 단위 다시 칠하기가 펼친 diff를 접지 않도록 카드 내용이 바뀔 때만 칠한다.
- goal 머리말이 「상태: 병합 대기 (PR N)」이면 「내 손이 필요한 일」 항목이 PR 번호를 싣고(`lib/progress.mjs` `judgeHand`의 `pr` 칸), 카드는 번호가 바뀔 때 한 번 그 PR을 불러온다. 다른 열린 PR은 아래 목록에서 고르고, 목록에 없는 PR(닫힌 PR 등)은 번호 칸으로 불러온다.
- 카드 — `#번호 제목`, `base ← head`, 짧은 머리 SHA(마우스를 올리면 전체), 바뀐 파일 수, 필수 검사와 결과, 막는 이유, 「꼭 볼 것」 파일 목록, 「병합」·「다시 읽기」, 결과 줄.
- 「꼭 볼 것」 파일마다 접힌 diff가 있다. patch가 있으면 펼칠 때, patch가 없으면(큰 diff·이름만 바뀜) GitHub 파일 diff 링크를 누를 때 본 것으로 친다.
- 「병합」은 서버 판정(`canMerge`)이 참이고 「꼭 볼 것」을 모두 본 뒤에만 켜진다(`chime.js` `AgentDeckMerge.mergeGate`). 본 기록은 PR·머리 SHA·경로로 메모리에만 둔다. 새로고침하거나 머리 SHA가 바뀌면 다시 봐야 한다.
- 「병합」을 누르면 결과가 올 때까지 「바탕화면의 확인 창에서 병합을 눌러 주세요」가 보인다. 한 번 보낸 SHA는 「다시 읽기」 전까지 다시 누를 수 없다.
- 색은 기존 뜻만 쓴다. 노랑 = 사용자가 할 일. diff의 더한 줄·뺀 줄은 기존 옅은 초록·빨강 면 토큰이다.

## 화면 — 열린 PR 목록 (M07 G11)

- 자리는 병합 영역 맨 위, 카드 위다. 항목마다 `#번호`, 제목, `base ← head`, 짧은 머리 SHA, 초안이면 「초안」 표시가 있다. 작성자·갱신 시각·전체 SHA는 마우스를 올리면 보인다. 서버가 준 글은 모두 페이지의 이스케이프 함수로 넣는다(`chime.js` `AgentDeckMerge.prListHtml`).
- 항목은 단추라 Tab·Enter로도 고른다. 누르면 번호 칸과 같은 길(`loadMerge`)로 아래 카드가 그 PR을 다시 읽는다. 고른 항목은 노랑 테두리와 `aria-current="true"`로 남는다. 고른 항목은 카드에 연 PR로 정하고, 카드가 비었으면 goal의 병합 대기 PR이다(`pickedPr`). 확인 창이 떠 있는 동안은 눌러도 카드를 바꾸지 않는다.
- 항목이 3개를 넘으면 목록이 항목 3개 높이(`--mg-row` 고정 높이 × 3)에서 멈추고 그 안에서 세로 스크롤한다(`.mg-list.is-scroll`, `overscroll-behavior: contain`). 페이지 전체는 늘지 않는다. 다시 칠해도 스크롤 자리와 누른 단추의 초점을 되살린다.
- 목록은 요약만 보인다. 필수 검사·「꼭 볼 것」·「병합」은 고른 PR 하나의 카드에서만 판정한다 — PR마다 여러 번 읽는 비용을 피하고 판정 길을 하나로 둔다(goal G11 결정 대장 [AI]). 목록의 머리 SHA는 보이기만 하고 병합에 쓰지 않는다. 병합에 쓰는 SHA는 언제나 카드의 읽기(`POST /api/merge/read`)에서 온다.
- 목록은 처음 그릴 때, 「목록 새로 읽기」, 병합 결과 뒤에만 읽는다. 스냅샷마다 `gh`를 부르지 않고, 실패해도 저절로 다시 읽지 않는다. 열린 PR이 없으면 「열린 PR이 없어요」 한 줄, 읽지 못하면 이유 한 줄이고, 번호 칸과 카드는 그대로 쓴다.
- 읽기는 `POST /api/merge/list {}` → `lib/merge.mjs` `listPrs` → `gh pr list --repo <origin의 owner/repo> --state open --json number,title,baseRefName,headRefName,headRefOid,isDraft,author,updatedAt --limit 51`(셸 없이 인자 배열). 50개까지 보이고 51번째가 있으면 「더 있음」을 알린다. 번호·SHA(40자리 16진수)가 꼴에 맞지 않는 항목은 빼고 수를 알리며, 나머지 칸은 꼴이 맞지 않으면 비운다. 실패 이유의 자격증명은 가리고 제어문자는 지운다.
- 목록 읽기는 보인 SHA·세대·보내기 표를 건드리지 않는다. 그래서 목록만 읽은 SHA로는 병합 준비가 열리지 않고, 카드가 읽어 둔 SHA는 목록을 다시 읽어도 그대로다. 병합 요청이 확인 창을 기다리는 동안에도 목록 읽기는 막히지 않는다.
- `gh pr list`를 고른 까닭 — 칸을 `--json`으로 좁혀 한 번에 받고, G10 감시(`gh pr view`)와 같은 꼴이다. 실패는 HTTP 상태가 아니라 stderr 평문(실측 `GraphQL: Could not resolve to a Repository …`)이라 REST 응답 판독(`parsePlain`)을 쓰지 않는다.

## 「꼭 볼 것」 판정 (`lib/merge.mjs`)

- 경로 — `.claude/`, `CLAUDE.md`·`AGENTS.md`(어느 깊이든), `98_Management/01_GateState/`, `.github/workflows/`. 대소문자를 가리지 않는다(작업 사본이 Windows라 `.Claude/`도 `.claude/`에 풀린다). 이름 바꾸기는 옛 경로도 본다.
- `package.json`(어느 깊이든) — patch 글자가 아니라 PR의 `base.sha`와 머리 SHA 두 쪽의 파일을 contents API로 읽어 `scripts` 객체를 비교한다(키 순서는 무시). 새 파일은 base를, 지운 파일은 head를 읽지 않는다. 이름 바꾸기·복사가 `package.json` 이름(대소문자 무시)에 닿으면 비교하지 않고 「꼭 볼 것」이다. 읽기·해석에 실패하면(404, 1MB를 넘어 `encoding: none`, JSON 아님) 「꼭 볼 것」이다.
- 파일 목록은 `per_page=100`으로 쪽을 넘긴다. GitHub 상한 3000개에 닿거나, 읽은 수가 PR의 `changed_files`와 다르거나, 한 쪽이라도 못 읽으면 판정을 다 못 한 것이라 병합을 막는다(`filesError`).
- patch는 「꼭 볼 것」 파일만 화면에 보낸다.

## 병합 길

경로는 셋이다 — 목록 `POST /api/merge/list`(읽기 전용, 위 절), 읽기와 병합(아래). 셋 모두 결정 응답과 같은 토큰·Origin·Host·64KB 검사를 거친다.

1. `POST /api/merge/read {pr}` — 서버가 PR을 읽고 그 머리 SHA를 「마지막으로 보인 SHA」로 기억한다(PR마다).
2. `POST /api/merge/run {pr, sha}` — 마지막으로 보인 SHA만 받는다. 받는 순간 소비하고 세대를 올린다. 그 전에 시작한 읽기가 늦게 끝나도 다시 무장하지 않는다.
3. PR을 다시 읽어 머리·base·열림·미병합을 대조한다. 다르면 창을 띄우지 않는다.
4. 확인 창을 띄운다. 창에는 서버가 읽어 둔 값(번호·제목·`base ← head`·전체 머리 SHA·「꼭 볼 것」 이름)만 보인다. 요청 본문의 글은 쓰지 않는다.
5. 결과가 정확히 `{ answer: 'yes' }`일 때만 보낸다. PR을 한 번 더 읽어 대조한 뒤 `gh api -i -X PUT …/pulls/N/merge-async -f sha=… -f merge_method=merge -f merge_action=direct_merge -F bypass_rules=false`.
6. 202면 `merge-async/{uuid}`를 2초마다, 90초까지 조회한다. 200·202·400·403·404·409·422와 상태 번호 없는 실패(「결과 모름」)의 뜻은 앱 서비스와 같다.

병합 요청은 한 번에 하나다. 창을 기다리는 동안 온 두 번째 요청은 409로 돌려보낸다.

## 사람 확인 창 (`lib/confirm.mjs`)

- 유일한 사람 증명이다. 페이지 토큰은 에이전트도 페이지에서 읽을 수 있어서, 토큰·출처 검사는 다른 사이트를 막을 뿐 사람을 증명하지 않는다.
- `powershell.exe -NoProfile -NonInteractive -STA -Command <고정 스크립트>`를 `execFile`로, 셸 없이, `windowsHide: true`로 띄운다. 스크립트는 작은따옴표만 쓰는 한 줄 고정 글이다.
- PR 제목·브랜치 이름·파일 이름은 남이 정하는 글이라 스크립트에 끼우지 않고 환경변수(`AD_MERGE_*`)로만 넘긴다. 제어문자와 글 방향 바꾸기 문자는 빈칸이 되고, 빈칸 연속은 하나로 접히고, 긴 글은 잘린다(제목은 120자). 제목은 창의 맨 끝 줄이라 위의 SHA·꼭 볼 것 줄을 흉내 내지 못한다. 물려받은 `AD_MERGE_*` 값은 버린다.
- 맨 위에 뜨는 창이다. 단추는 「병합」·「취소」이고 가속키가 없다. 첫 초점은 「취소」, 뜬 뒤 1.5초는 두 단추가 잠긴다. Enter 기본 단추는 없고, 창 닫기·Esc는 취소다.
- 키보드로는 확인되지 않는다. 「병합」은 마우스 왼쪽 클릭(`MouseClick`)에만 반응하고 Tab 순서에서 빠진다. 화살표·Tab으로 초점이 가도 Enter·Space는 `Click`만 일으켜 병합하지 않는다(2026-11-18 시험 폼 실측: Space·`PerformClick`은 `Click`만, 마우스 왼쪽 클릭만 `MouseClick`). 타자 중이던 「↑ Enter」나 「Tab Enter」가 확인으로 새지 않게 하려는 것이다(PR 75 검수).
- 확인은 「병합」을 눌렀을 때만 나오는 전용 출력 한 줄(`AGENTDECK_MERGE_CONFIRMED`)과 정상 종료로만 판정한다. 비정상 종료·빈 출력·다른 출력·시간 초과·창을 띄우지 못함·Windows 아님은 모두 취소다. 동시에 한 창만 띄운다.
- 시간 초과는 기본 120초다. 창은 띄운 시각 기준 마감(죽이기 2초 전, `AD_MERGE_DEADLINE`)에 스스로 닫힌다. 마감이 뜬 시점이 아니라 띄운 시점 기준이라, PowerShell 기동이 늦어도 창이 열린 채 죽지 않는다.
- 실측(2026-11-18): `windowsHide: true` 자식에서 그냥 띄운 폼은 보이지 않았다(바깥에서 본 `MainWindowHandle` 0). 숨김 자식의 첫 `ShowWindow`가 `SW_HIDE`를 물려받기 때문으로 본다. 창이 뜬 직후 `WindowState`를 Minimized → Normal로 바꾸니 보였다(손잡이와 제목 확인, 누르지 않고 스스로 닫힘).

## 주입 지점

`createDashboard(config, deps)`가 병합 서비스(`prService`), 확인 함수(`confirm`), 확인 창 시간 초과(`confirmTimeoutMs`), 확인 뒤 보내는 함수(`mergeFn`, 없으면 `prService.sendMerge`)를 함수 인자로만 받는다. 환경변수나 설정 파일로는 바꿀 수 없다. 시험과 실측용 서버는 가짜를 넘긴다 — 실측용 서버는 `mergeFn`에 호출을 기록만 하는 함수를 넣는다.

## 병합 완료 감지 (M07 G10)

- PR을 만든 세션은 저장소 루트에서 `node 99_Others/Dashboard/wait-merge.mjs <번호>`를 백그라운드 명령으로 건다. 사용자가 어느 길로 병합하든(이 카드, 앱 PR 카드, GitHub 웹, 직접 치는 `gh pr merge`) 명령이 끝나며 세션이 다시 불린다.
- `gh pr view <번호> --repo <origin> --json state,mergedAt,mergeCommit,mergedBy,headRefOid`를 30초마다 읽기만 한다(`lib/waitMerge.mjs`). 저장소는 실행 파일 위치에서 구한 저장소 루트의 origin으로 고정한다 — 세션의 cwd·`GH_REPO`에 기대지 않는다.
- 끝: 병합되면 `MERGED pr=… commit=… at=… by=… head=…`와 0, 병합 없이 닫히면 `CLOSED`와 3, 읽기 실패면 `ERROR`와 2, 잘못된 번호는 64다.
- 읽기 실패는 둘로 나눈다. 없는 PR·저장소 밖·인증 실패·gh 없음(2026-11-18 실측 문구)은 첫 읽기에서 `ERROR … permanent`로 끝난다. 나머지는 간격을 두 배씩 늘려(최대 5분) 다시 읽고, 연달아 10번이면(약 37분) `ERROR … transient`로 끝난다. 오류 글의 자격증명은 가린다.
- 출력 값은 꼴이 맞을 때만 싣고(40자리 16진수, ISO 시각, GitHub 로그인) 나머지는 `unknown`이다. 남이 정한 글이 세션에 그대로 흘러가지 않게 하려는 것이다.
- 출력은 방아쇠일 뿐이다. 끝난 뒤 세션이 할 일(병합이면 종결 기록까지만, 닫힘이면 알림, 오류면 한 번 다시 걸기)은 헌법 11조가 정한다. 다음 goal은 열지 않는다.
- 감시는 세션이 닫히면 사라진다. 세션을 다시 열면 SessionStart 훅(`.claude/hooks/10_start-brief.cjs`)이 pin의 현재 goal 줄에서 「(병합 대기, PR N)」을 찾아 감시를 다시 걸라는 줄을 주입한다. compact 때는 같은 세션이 이어지므로 주입하지 않는다. 감시는 PR마다 메인 세션 하나만 건다.
- 결정 응답처럼 메인 입력창에 넣는 방식은 쓰지 않았다(2026-11-18 사용자 결정). Enter까지 누르면 입력창에 남은 글이 함께 제출되고, 넣기만 하면 사람이 Enter를 눌러야 해서 「바로」가 안 된다.

## 한계 (L3)

- 에이전트가 `node`로 병합 모듈을 부르거나 `gh api`를 직접 부르면 이 길을 거치지 않는다. 화면 자동화로 확인 창의 「병합」을 누를 수도 있다. 이 장치가 막는 것은 실수와 무심한 자동 진행이다. 신원·토큰 분리(단계 B·C)는 이 goal의 범위 밖이다.
- 「꼭 볼 것」 펼침 게이트는 화면 쪽이다. 주소를 직접 부르면 건너뛰므로 확인 창이 같은 파일 이름을 한 번 더 보인다.
- `package.json`의 비교 기준은 PR의 `base.sha`라서, base가 그 뒤 `scripts`를 바꿨으면 PR이 건드리지 않았어도 「꼭 볼 것」이 될 수 있다(닫힌 쪽 오판).
