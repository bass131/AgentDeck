# 쟁점 06 — 분업 라우팅 규격 표: 복잡도를 모델이 판단하지 않게

**질문 한 문장**: "이 일을 누가 하는가"(단일→메인 / 도메인→Worker / 병렬→크로스 / 대규모→팀)의 분류 자체를 모델의 재량이 아니라 **관측 가능한 규격**으로 바꾸는 표는 무엇인가?

## 왜 지금

- 03장 분업 1 행의 승격 전제: "라우팅 규격을 표로 확정하면 '복잡도를 모델이 판단하지 않는다'가 성립해 G로 승격할 수 있다 — Agent Ochestration 페이지의 미승격 자산."
- 카드 5가 경계(방향/작성)를 그었으니, 남은 절반은 "작성 이후의 실행을 **누구에게** 주는가"다.
- 부트스트랩(쟁점 08)에서 Worker·스폰 게이트를 실물로 만들 때 라우팅 표가 없으면 스폰 조건을 쓸 수 없다.

## 원 자산 (Agent Ochestration 페이지, 2026-04-17)

- 라우팅 스케치: 단일 요청 → 메인 / 특정 도메인 작업 → 도메인 Worker / 병렬 작업 → 크로스 도메인 Worker / 신규 큰 규모 → 에이전트 팀 구성.
- 핵심 원칙 (원문): "복잡도 기준도 모델 자체가 판단하지 않음. 규격 내에서 단순 작업이라 판단 되는 경우만 실행함."
- 부속 자산: 검수 체인 — 리뷰어 1차 → codex 2차(교차 모델) → 메인 판단 → Worker 재작업 → 리뷰어 3차. (라우팅과 별개 자산 — 이 카드의 범위 밖, 처분은 부속 결정)

## 핵심 독해 — 카드 3·4와 같은 수(手), 세 번째 적용

"복잡도"는 "실패 횟수"(카드 3)·"판단 비중"(카드 4)과 같은 추상량이다.
같은 환원을 적용한다: **복잡도를 재지 말고, 계획 문서의 구조를 세라.**

카드 5 확정으로 실행 전에 항상 검증 통과한 Phase-Steps 문서가 존재한다.
그 문서에 Phase별 **도메인 태그**와 **의존성 표기**를 의무화하면, 라우팅은 문서를 읽는 기계 연산이 된다:

| 관측 신호 (계획 문서 실측)                          | 라우트                        |
| ----------------------------------------- | -------------------------- |
| 도메인 태그 종류 = 1, Phase 의존성 직렬                | 해당 **도메인 Worker** 단독       |
| 도메인 태그 종류 ≥ 2 또는 독립 Phase 묶음 ≥ 2          | **크로스 도메인 Worker 병렬** — 독립 묶음마다 하나 |
| Phase 수 > 스킴 상한(1~8) 또는 신규 프로젝트           | **대규모 처리** (분할 또는 팀 — 부속 결정) |
| (루프 밖) 산출물 변경이 없는 요청 — 질문·조회·자문           | **메인 직접** — 계획 불요          |

강제 구조(fail-closed): 도메인 태그·의존성 표기가 없는 계획은 검증 불통과 — 결정 대장 부재 = 반려(순서 4)와 같은 문법.
Phase-Steps 문서가 점점 기계 판독 가능한 상태 기계가 되어 간다: 검증 기록(카드 3) + 결정 대장(카드 4) + 도메인·의존성(카드 6).

### 정직한 한계 — 입구 분류는 순수 G가 불가능하다

표의 마지막 행("루프 밖 → 메인 직접")만은 자연어 해석이라 셀 수 없다 — 누군가는 요청을 읽고 "변경이 있는가"를 판단해야 한다.
규격이 하는 일은 판단의 제거가 아니라 **애매함의 방향 고정**이다: 변경 가능성이 조금이라도 있으면 루프행 (fail-closed).
나머지 세 행은 계획 문서 실측이라 G가 성립한다 — 표 전체로는 "입구 한 칸만 P+방향 고정, 본체는 G".

## 결정거리

### ① 라우팅 판정의 입력 — **확정 (2026-08-01, 영호): 방식 A**

계획 문서의 구조 신호. Phase-Steps 문서에 도메인 태그·의존성 의무화, 스폰 게이트가 표를 적용.
태그 없는 계획은 검증 불통과(fail-closed).
(기각: B 라우터 모델 분류 — P를 P로 바꾼 것 / C 사람 수동 지정 — 매번 결정 비용, 검증 3 위배.)

### ② "단일 요청 → 메인" 행의 v2 해석 — **확정 (2026-08-01, 영호): 무변경 요청만 메인**

질문·조회·자문은 루프 밖 — 계획도 Worker도 불요. 산출물 변경이 있으면 크기 무관 루프+Worker.
원칙 1("실무는 전부 SubAgent에게 위임")과 무충돌.

### ③ 대규모 라우트의 실체 — **확정 (2026-08-01, 영호)**

"대규모"는 하나의 현상이 아니라 셋이고, 관측 신호와 응답이 각각 다르다 (분해 채택):

| 현상          | 관측 신호 (계획 문서 실측)       | 응답 후보                                  |
| ----------- | ---------------------- | -------------------------------------- |
| **계획이 넘침**  | Phase 수 > 스킴 상한(1~8)   | **Milestone 분할** — 재계획으로 되돌림 (계획 층의 응답) |
| **감독이 넘침**  | 독립 병렬 묶음 수 > K (K 미정)  | **팀 구성** — 조정자를 세워 감독을 위임 (실행 층의 응답)   |
| **기반이 없음**  | 표준 레이아웃 인스턴스 부재 (신규)   | **부트스트랩 절차** — 라우트가 아니라 전용 절차 (쟁점 08)  |

- 상한값 "8"은 F3(1~8 Steps 파생 값)의 소유자 지정과 함께 처리 — 라우팅 규칙은 값을 복제하지 않고 mention으로 참조한다.
- **K(감독 폭 상한)는 실측 후 확정** (영호 결정) — 근거 없는 수를 박지 않는다. 그 전까지 대장에 미정으로 등재.
- **팀의 실물은 환경별 이원화** (영호 결정):
  - Claude Code 환경 — **중첩 SubAgent(기본 3단계, v2.1.219+) · Agent Teams**. 형제 SubAgent 간 SendMessage 직접 통신 지원(v2.1.206+) — 팀 요건(통신)이 Claude Code 안에서도 성립한다.
    ⚠️ 정정 (2026-08-01, 실측): 초기 기록 "위계가 평평(SubAgent가 SubAgent를 못 부름) → 평평한 Worker 풀 + 조정 문서"는 낡은 전제였다 — 영호 지적 후 공식 문서(code.claude.com/docs/en/sub-agents.md · agent-teams.md)로 확인·정정. 발화 프로브 실측은 파일럿 몫.
  - Orca 환경 — **서로 통신하는 멀티세션**. UI는 Terminal 오른쪽 분할, 새 창은 금지.
- 정밀 주석 (영호 정정, 2026-08-01): AgentDeck은 하위 서브에이전트 관리 형태이고, 멀티 세션 기능은 있으나 세션 간 **통신 파이프가 없다**.
  팀의 요건은 세션 수가 아니라 **통신**이다 — 통신 없는 멀티 세션은 팀이 아니라 독립 작업자들의 병렬일 뿐이다.

### ④ 검수 체인 — **확정 (2026-08-01, 영호): 크로스 도메인 라우트 이상급은 교차 검수 진행**

검수 강도를 라우트 등급에 연동한다 — 라우팅 표에 **검수 열**이 추가된다:

| 라우트            | 검수                           |
| -------------- | ---------------------------- |
| 도메인 Worker 단독  | 리뷰어 1차 (검증 2 기본)             |
| 크로스 도메인 병렬 이상  | 리뷰어 1차 + **codex 교차 모델 2차**  |

근거: 크로스 병렬은 도메인 간 통합점에서 결함이 나기 쉽고, 같은 모델 계열의 리뷰어는 같은 사각지대를 공유한다.
확증편향 차단의 세 번째 축이다 — 역할 분리(검증 2) · 시간축 분리(쟁점 13 Clear) · **모델 분리(교차 검수)**.
검수 열도 라우트의 함수라 모델 판단이 안 낀다 — G 성립에 지장 없음.
