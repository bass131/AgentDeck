# 쟁점 04 — 주도권 게이트 발동 신호 정의

**질문 한 문장**: "AI의 판단 비중이 사용자보다 커지면"(00장 원칙 2)을 모델의 자기 평가가 아니라 **관측 가능한 신호**로 바꾸는 정의는 무엇인가?

## 왜 지금

- 00장 원칙 2·플로우 ②의 주도권 게이트는 발동 조건이 "판단 비중이 커지면"이라는 추상량이다.
- 그 비중을 판정하는 주체가 지금은 **모델 자신**이다 — 자기 판단이 과한지를 자기가 판단하는 자기 참조 구조라, 03장 기준으로 순수 P다.
- 실패 방향도 나쁘다: 게이트가 발동을 잊으면 아무 신호 없이 그냥 진행된다 (fail-open). 잘못된 전제 위에서 루프가 돌기 시작하는 것을 막는 게 존재 이유인데, 그 문 자체가 조용히 열려 있다.

## 설계의 핵심 — 비중을 재지 말고, 결정을 세라

쟁점 03과 같은 수(手)다.
"실패 횟수"라는 세션 기억의 추상량을 FAIL 줄이라는 셀 수 있는 실물로 바꿨듯이,
"판단 비중"이라는 추상량을 **계획 속 결정의 출처 목록**이라는 셀 수 있는 실물로 바꾼다.

### 방식 A — 결정 대장 + 출처 태그 (추천)

계획 작성 SubAgent는 Phase-Steps 문서에 「결정 대장」 절을 반드시 만든다.
계획이 내리는 주요 결정마다 한 줄 + 출처 태그:

```
### 결정 대장
- [USER] 스택: Electron + React — 사용자 지시 (요청 원문에 명시)
- [AI] DB: SQLite — 로컬 단일 사용자로 추정
- [AI·비가역] 저장 스키마 v1 — 마이그레이션 도구 없이 시작
- [USER·위임] 폴더 구조 — "알아서 정리해줘"로 위임받음
```

발동 판정은 게이트가 태그를 세는 기계 연산이다:

| 조건                        | 판정                              |
| ------------------------- | ------------------------------- |
| `[AI·비가역]` ≥ 1            | **즉시 발동** — 개수 무관               |
| `[AI]` 수 > `[USER]` 수     | **발동** — "판단 비중이 사용자보다 커지면"의 문자 그대로의 구현 |
| 결정 대장 절 자체가 없음            | **계획 반려** — 대장 부재 = 검증 불통과 (fail-closed) |

발동하면 계획 실행(구현 루프 진입)이 막히고, 소크라테스 문답으로 분기한다.
문답의 재료가 곧 `[AI]` 줄들이다 — "이 계획에는 네가 말하지 않은 결정이 셋 있다. DB는 SQLite로 추정했는데 맞아?"
사용자가 답하면 해당 줄의 태그를 `[USER]`로 바꾸고 답을 병기한다 — 쟁점 03의 기준점 이동과 같은 문법으로, 기록은 지우지 않고 상태만 전환된다.
태그 전환 후 모호성 게이트부터 재확인한다 (00장 플로우 ② 기존 흐름 유지).

이 방식이 기존 규칙들과 맞물리는 지점:

| 기존 규칙                    | 방식 A에서                                      |
| ------------------------ | ------------------------------------------- |
| 원칙 4 — 문서가 진실의 원천        | "누가 이 결정을 내렸나"가 세션 기억이 아니라 계획 문서에 산다        |
| 검증 3 — 게이트 강도는 가역성으로     | 비가역 AI 결정만 무조건 발동 — 게이트 강도가 가역성을 따라간다       |
| 산출물 1 — 사람 관측성           | 사용자가 계획을 열면 "내가 정한 것 / AI가 추정한 것"이 한눈에 갈린다  |
| 쟁점 03 — 잊음의 방향           | 대장을 안 쓰면 발동이 안 되는 게 아니라 계획이 반려된다 (fail-closed) |

### 방식 B — 휴리스틱 체크리스트

위임 어휘("알아서", "적당히") 감지, 요청 길이 대비 계획 길이 비율, 처음 다루는 도메인 여부 같은 신호 목록을 두고 모델이 점검한다.
장점: 계획 작성 전에 이른 발동이 가능하다.
단점: 각 신호의 판정이 다시 판단 층이다 — P를 P의 목록으로 바꾼 것이라 보장이 안 생긴다.

### 방식 C — 상시 발동

모든 계획이 소크라테스 문답을 최소 1회 통과해야 실행된다.
장점: 가장 단순하고 누락이 없다.
단점: 사용자가 전부 지시한 계획에도 문답이 돌아 잔소리가 된다 — "모든 게이트를 같은 강도로 걸면 정작 중요한 게이트가 요식이 된다"(검증 3)에 정면으로 걸린다.

## 부속 결정

- **대장 등재 기준**: 모든 선택이 아니라 **계획 수준의 결정**만 — 스택·구조·범위·데이터·UX 방향처럼, 나중에 사용자가 "왜 이렇게 했어?"라고 물을 수 있는 선택.
  변수명 급의 세부는 등재하지 않는다 (대장이 비대해지면 판정이 소음에 묻힌다).
  세부 기준·템플릿은 2권(세팅·실행예시본)과 부트스트랩의 몫.
- **명시 위임 처리**: 사용자가 "알아서 해줘"라고 위임한 영역의 결정은 `[USER·위임]` — 위임 자체가 사용자의 결정이므로 발동 계산에서 USER 쪽으로 센다.
  **단, 비가역 결정은 위임으로 못 덮는다** — `[AI·비가역]`은 위임 여부와 무관하게 발동한다.
  근거: 파괴적 작업을 포괄 위임("정리해줘")으로 처리하다 난 사고의 실측 — 비가역은 이름 확정 목록으로만 승인된다는 운영 교훈과 같은 결.
- **문답의 실물 형식**: 열린 질문이 아니라 **선택지형 질문**(추천안 명시 + 대안 + 직접 입력)을 기본으로 한다.
  이 논의 자체가 실증 사례다 — 쟁점 2·3·4가 전부 선택지형 문답으로 결정됐고, 열린 질문보다 사용자의 결정 비용이 낮았다.

## 승격안 (확정 시)

1. **02장 순서의 규칙 4 신설** — "계획의 결정에는 출처를 태그한다" + 강제 구조(발동 판정 표·fail-closed) 한 세트.
   말미 "열두 개" → "열세 개".
2. **03장 매핑 표에 행 추가** (운영 규칙 1: 규칙과 행은 한 세트) — 현재 **P** ⚠️ / 목표 **G+S**.
   승격 경로에 확정 설계 서술. ⚠️ 집계 문장 "두 곳" → "세 곳".
3. **00장 원칙 2·플로우 ② 보강** — "판단 비중이 커지면"에 관측 가능 정의를 연결 (기준 소유는 02장 신설 규칙 — F2와 같은 소유권 문법).
4. 결정 대장 템플릿·문답 형식은 이 문서가 보관 — 실물은 부트스트랩(쟁점 08) 때.

## 추천 (Claude, 2026-08-01)

방식 A + (비가역 ≥ 1 즉시, AI 과반 발동) + 위임은 USER로 세되 비가역은 예외.
이유 한 줄: "판단 비중이 사용자보다 커지면"이라는 원문이 방식 A에서는 은유가 아니라 **문자 그대로 계산 가능한 문장**([AI] 수 > [USER] 수)이 된다 — 규칙 문장을 바꾸지 않고 P를 G+S로 올리는 유일한 길이다.

## 결정

**확정 (2026-08-01, 영호)** — 방식 A(결정 대장 + 출처 태그) + 발동 기준(비가역 ≥ 1 즉시, [AI] 과반 발동) + 위임=USER·비가역 예외.
"판단 비중이 사용자보다 커지면"을 계획 문서 「결정 대장」의 태그 계산으로 환원한다: `[AI·비가역]` ≥ 1이면 즉시, `[AI]` 수 > `[USER]` 수면 발동해 소크라테스 문답으로 분기하고, 대장이 없는 계획은 검증 불통과(fail-closed).
답변은 태그를 `[USER]`로 전환(기준점 이동 문법), 위임은 USER로 세되 비가역은 위임으로 못 덮는다.

**승격 목록** (2026-08-01 노션 반영 완료, fetch 대조 검증):

  현재 열은 P 유지 — 실물 반영은 부트스트랩(쟁점 08) 때, 그때 G+S로 갱신.
